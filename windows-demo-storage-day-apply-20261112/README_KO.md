## 적용과 자동 확인

기존 핵심 소스 55개·제어 의존 파일 66개를 검증하고, 같은 GET 전용 검증으로 잔고·현재 계정 전체 노출·알려진 청산 및 BTC 체결 이력·수입 내역을 새로 확인합니다. 미리보기 출력만 재사용해 적용하지 않습니다. 정상 합성 적용은 30회 HTTP 요청이며 기존 최대 48회/75초 읽기 제한, 요청 여유 검사 및 418/429 재시도 금지를 유지합니다.

이후 계정 리스를 확보하고 PostgreSQL 공유 범위 읽기 잠금과 두 저장소 파일 읽기 잠금을 보유한 상태에서 현재 노출을 다시 확인합니다. 30초 이내인 마지막 계정 증거, 현재 일/주, 같은 원장, 같은 저장소/독립 체크포인트를 확인한 경우에만 트랜잭션으로 적용합니다. 계정 리스는 finally에서 해제합니다.

실제 변경은 일간 날짜·기준금액과 새 AttestedDayBaseline/operation 영수증 추가 및 리스/적용/해제 감사 이벤트입니다. 기준금액 수치는 기존과 같습니다. 이전 모든 영수증과 감사 이력은 그대로 남깁니다. 새 영수증에는 이전 원장 전체 해시와 보존 영역 해시를 기록합니다. 검증 시 새 영수증만 제거하고 일간 필드를 이전 값으로 복원한 사본이 정확히 이전 원장과 같은지 확인하여 기존 11월 7/9/11일 및 저장소 영수증 체인을 검증합니다. 기존 영수증의 해시를 새 값으로 덮어쓰지 않습니다.

주간 기준·고점·이전 평가 시각·청산 이력·실패 trial·요청 이력·설정/바인딩·주문/공유 SQLite·시계 복구 원본과 intent·PostgreSQL 체크포인트는 바꾸지 않습니다. 소스 설치·컨테이너 교체·저장소 초기화·주문 writer session·거래 실행은 하지 않습니다.

정확한 자정 평가와 전체 종목 과거 거래 export는 확보했다고 주장하지 않으며 해당 필드는 false입니다. 출처는 사용자의 계정 전체 무활동 확인과 서명된 USDT/청산/현재 상태 증거입니다.

적용 후 내부 읽기 전용 postcheck를 수행합니다. 그 다음 CMD가 기존 `scripts.check_demo_session_ready`로 별도의 최신 거래소 준비 확인을 한 번 실행합니다. 이 추가 조회도 DB를 바꾸거나 진입을 재개하지 않습니다. 성공 마지막 문구는 다음과 같습니다.

```
DAY12_APPLIED_READ_ONLY_READY_KEEP_PAUSED_NO_ORDERS
```

적용 JSON의 `storage_day_adoption`은 `OPERATOR_ATTESTED_DAY12_ADOPTED_ENTRIES_STILL_PAUSED`, `database_changed`는 true입니다. 뒤이어 `session_ready: READ_ONLY_READY_ENTRIES_STILL_PAUSED`, `period_keys_match: true`를 확인합니다. 실행 승인·주문·실거래는 false를 유지합니다. 이것이 실제 TP 실행 조건의 해결이나 거래 승인이라는 뜻은 아닙니다.

## 중단 및 재확인

DEMO 키 세션은 기존 것을 프롬프트 없이 읽으며 자동 삭제/재등록하지 않습니다. 세션이 없으면 적용 전에 중단합니다. 값이 달라졌거나 날짜·노출·수입·저장소에 변화가 있으면 임의로 채우거나 기간을 확장하지 않고 중단합니다.

DB 응답이 유실되면 `application_may_have_completed`가 true일 수 있습니다. 결과를 추정해 원장을 되돌리거나 다시 기준값을 덮어쓰지 마세요. 포함된 아래 명령으로 새 영수증과 기존 체인을 읽기 전용 검증할 수 있습니다.

```bat
RUN_POSTCHECK.cmd
```

이미 적용된 같은 영수증은 추가 GET이나 리스/감사 이벤트 없이 검증합니다. 새 날짜가 됐으면 postcheck는 현재 기간 불일치를 표시하며 자동 연장하지 않습니다. 이전 11월 11일 전용 설치/기간 적용 스크립트는 다시 실행하지 마세요. 현재 영수증 체인 확인에는 이 패키지의 RUN_POSTCHECK.cmd를 사용합니다. 후속 준비 확인만 실패했다면 일간 적용이 취소된 것은 아닙니다. 마지막 JSON을 공유하세요.
