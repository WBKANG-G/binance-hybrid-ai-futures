# Drain owned confirmation workers before cleanup

The single-owner scheduler prevented a replacement loop but still awaited asyncio.to_thread directly. Cancelling its awaiting task could finish the call while its worker continued, mark the claim inactive and permit journal cleanup. Direct confirmation calls outside session.run also did not block close. Closing before any confirmation did not close the confirmation admission gate. Six baseline cases reproduce these ordering gaps with actual blocked threads and stubbed renew/clock/position/proof operations; they do not fabricate signed proof or exchange traffic.

The four owned confirmation stages now use the repository's existing settled_call utility: lease renewal, SDK clock refresh, physical-position read and original full proof. It shields the worker, drains completion despite repeated cancellation, consumes a worker exception without logging details, then rethrows the caller's cancellation. The ownership claim remains active during draining. ManagedRuntimeSession.run therefore keeps its original settings and journal ownership until that awaited work settles; its existing finally then disables settings and permits cleanup.

ConfirmationClaim also closes admission atomically against a start claim. Runtime close refuses an active direct confirmation before revoking the budget or closing its journal. Inactive close permanently closes that gate, so a first confirmation attempted after close returns UNKNOWN before a clock/renewal read. The claim lock is released before budget revocation, journal close, HTTP or await. A local journal-close failure retains the closed admission gate and existing revoked budget; the original local cleanup retry remains possible without reopening execution.

No worker is forcibly stopped. Cancellation can be delayed beyond the start deadline while an original operation settles. If the underlying operation never returns, this path keeps waiting and holds ownership; it does not pretend that cleanup is safe or promise a hard wall timeout. The guarantee concerns these four owned stages, not arbitrary detached tasks elsewhere. A worker may commit genuine original proof while its caller is canceled; the existing signed records/seal remain untouched, and cancellation is still not reported as a fresh VERIFIED_FLAT result.

The existing first-outcome, no-reset, duplicate refusal, start deadline, attempt/deferral limits, fencing, original proof, order UNKNOWN records and transport-cost accounting remain in force. There is no new request route, POST retry, force-release, journal repair, refund or trading activation.

Tests cover the six original failures, repeated cancellation with worker failure, actual runtime.run settings/lock order, and atomic close/start races. Blocked worker tests use events and do not wait out the production start deadline. Existing single-owner/deadline/runtime cleanup tests remain unchanged except for additional close-admission assertions. Separate synthetic TP and partial-fill lifecycle tests still need the original full-flat proof and no-wire repeated confirmation. Docker uses a blocked fake worker and claim without network or database/order bridge; it does not establish a financial proof.

Lifecycle startup holds are accelerated and observation is 0.8 seconds; request-weight timing is real. These are not new 300-second natural observations or actual exchange measurements. Installed historical production files, the canonical CLI and the reused settled_call implementation are byte-identical.

Actual account order usage, external IP capacity and complete request-cost bounds remain unproven. Default production execution stays disabled. No Windows installation/database change, real exchange request/order or trading resume occurs in this review.
