# Review outcomes distinguish returned proof and runtime failures

The preceding diagnostics exposed the scheduler's original-proof stop reason; quota seal failure and session/bridge failure were separate internal flags (bridge degradation also appeared in the existing managed-quota report). The new review outcome combines these facts without changing the underlying confirmation, quota seal, cleanup or approval behavior. Ten initial report-fixture cases lacked this new classification on the prior source; these are expected missing-report-feature tests, not ten demonstrated trading failures.

confirmation_diagnostics now reports a classified owner outcome, its returned flat-confirmation stamp, quota_seal_failed, session_failed, captured bridge degradation, and completed attempts. Categories cover not started/running, returned proof, proof with seal/session/bridge failure, cancellation, start deadline, limit, context rejection and original operation failure. Existing scheduler stop reasons and counters remain available. The captured original bridge is used so a changed public alias does not redirect diagnostics.

The returned stamp is the first scheduler owner's reported proof; it is not the return value of a later refused repeat, a fresh exchange observation or a statement that every underlying database action finished. A canceled worker can have committed original records while the owner did not return proof; those records are preserved and this report does not infer them. Reading diagnostics performs no SQL, transport, reservation, seal, repair, or account/event/outbox/journal write.

Every category explicitly retains execution_approved=false and next_action=KEEP_PAUSED_REVIEW_ONLY. financial_database_rechecked=false and quota_seal_verified_from_records=false mean the report did not recheck storage, not that every seal failed. quota_seal_failed is the original failure flag; a false flag is not a new affirmative storage proof. The original financial and managed quota records remain the authority. No cached success is reused as execution permission.

Eleven read-only report-fixture tests cover distinct states, including bridge-only degradation. Their injected labels are input data, not financial proof. Separate assembled lifecycle tests run the original full TP proof, partial-fill cleanup, and TP proof with only quota sealing deliberately failed. The last case must preserve the genuine financial flat proof while retaining an unsealed flow, original failure/degraded flags and the explicit PROOF_VERIFIED_QUOTA_SEAL_FAILED review outcome. Normal cases require sealed flows and classification matching their actual session flag; all cases stay paused and disabled. Repeated confirmation still produces no extra wire rows.

The full lifecycle traces record unsealed-flow counts for test evidence; the generic diagnostics themselves never query them. Docker smoke uses a report-state fixture without SDK, database, financial proof or network and checks classification/default refusal only. Tests use isolated synthetic HTTP/WSS/PostgreSQL, accelerated startup holds, 0.8-second observation and real request-weight timing. These are not new 300-second natural observations or actual exchange measurements.

Original signed proof, seal failure handling, reservation accounting, process ownership, cancellation draining, start deadlines and canonical CLI are unchanged. Worker draining can still delay cancellation until original work returns; no whole-function hard wall timeout is claimed. Actual account order usage, external IP capacity and complete cost bounds remain unproven. Default production execution stays disabled. No Windows installation/database change, real exchange request/order or trading resume occurs in this review.
