# Confirmation start deadlines — opt-in runtime review

The historical budgeted confirmation loop checked its 120-second deadline only after a ProofDeferred exception. Renewal, clock refresh, physical-position checks, completed UNKNOWN attempts and sleeps could cross that deadline and still start another phase. Six scheduler-only baseline cases reproduce this ordering gap. They stub lease/position/proof scheduling, return only UNKNOWN and do not simulate a successful signed proof or actual exchange traffic.

The explicit runtime now assembles RuntimeConfirmationCoordinator, a subclass of the original managed coordinator. Only its confirmation scheduling loop changes. It keeps the original physical-position validation, complete signed/historical flat proof, managed flow sealing, fencing, idempotency and reduce-only protections through inherited methods. The historical coordinator, SDK, wire budget and canonical CLI remain byte-identical.

Each invocation gets one fixed 120-second monotonic start window. Checks before and after renewal/refresh/position work and cost admission prevent starting another phase after expiration. Sleeps use min(1 second, remaining time). The original four completed attempts remain the limit. At most 120 resource deferrals are allowed even if an injected clock stalls. Nonfinite/backward/failing clocks return UNKNOWN. Stop diagnostics separate deadline, deferral/attempt limits, exposure, operation errors and caller cancellation. UNKNOWN never establishes flatness or seals an unresolved flow.

This is a start deadline, not a whole-function hard wall timeout. Already-started work settles through the original transport/confirmation bounds; worker threads are not forcibly abandoned. A genuine already-started original proof may finish and report VERIFIED_FLAT after the start window. Its committed result is not discarded or relabeled merely to manufacture a timeout. No new phase starts afterward. Caller cancellation and original operation failures still propagate; this scheduler does not claim to stop an already-running thread. The diagnostic explicitly says whole_function_wall_time_limit_proven=false.

The deadline does not reserve venue capacity, extend header freshness, refund attempts, remove history, relax proof requirements or retry POSTs. It adds no exchange route and cannot authorize execution. All individual calls retain the existing admission/ownership checks. The old parent scheduler is intentionally left untouched because installed historical source pins are preserved; this new scheduler applies only through the opt-in assembly.

Twenty-five focused tests cover six baseline phase-order cases, deadline arithmetic/boundaries, clipped waits, four UNKNOWN attempts, finite deferral cap with a stalled clock, clock regression, slow cost checks, exposure, original exception propagation and caller cancellation. Scheduler tests stop short of the real financial proof. Separate original TP and partial-fill lifecycle tests must still establish actual full-flat proof against synthetic HTTP/WSS/PostgreSQL. Their raw evidence includes the new scheduler diagnostics.

Lifecycle startup holds are accelerated and observation is 0.8 seconds; request-weight timing is real. These are not new 300-second natural observations or exchange measurements. Docker smoke checks arithmetic/imports/default refusal without network; it does not exercise the full scheduler or PostgreSQL.

Actual account order usage, external IP capacity and complete cost upper bounds remain unproven. Default production execution stays disabled. No Windows installation/database change, real exchange request/order, or trading resume occurs in this source review.
