# Bind confirmation phases to the original runtime context

Confirmation entered lease renewal before checking its runtime bindings. Later SDK signing, request admission and original fencing checks still existed, but replaced coordinator/proxy/provider references could reach scheduler work first. Thirteen baseline cases reproduce missing early rejection with stubbed scheduler operations: store, lease, client, budget, bridge, proxy bridge/engine, bridge store/journal, credentials, settings, costs and shared scope. These are boundary-order tests, not demonstrations of an actual foreign database write or unauthorized exchange request.

The runtime coordinator captures its original managed store/client/budget/bridge/lease/journal and database engine at construction. A factory-supplied callback reuses the owned budget's frozen model/transport/provider checks under its lifetime lock, rejects revocation and known untrusted state, and leaves stale-but-trusted metadata available for the original scoped refresh. The original bound client's credential/settings checks are reused; the legitimate demo_trading_enabled transition stays allowed. Capacity-only stops still use the existing cleanup policy.

Bindings are checked before the initial clock/window/renewal and at phase boundaries, including after renewal, refresh, position observation and cost admission. Each settled worker checks again at entry after async dispatch. Store renewal and SDK clock work use captured owner references. The result of original proof work is checked before it is accepted as this call's successful outcome. The caller's first exception remains visible and the single start claim is consumed; repeated calls do not retry a rejected context.

A context rejection adds no reservation, replacement context or repair. Existing upstream intents, pending transport/order records and any original proof already committed by a worker are not rolled back or relabeled. A late binding rejection can prevent a new successful return even if underlying original records have committed. Close still acts on captured owned resources and uses the separate atomic close/start gate; changed aliases do not redirect cleanup to another journal.

These are consistency checks at explicit boundaries, not a replacement for effect-time fencing, SDK validation or per-request admission. Lease expiry/ownership is still checked by the original renewal and fenced effects. Checks do not reset daily/weekly keys, widen request shapes, claim external capacity, or make arbitrary Python attribute mutation atomic. The installed historical SDK/coordinator/CLI and original full-flat proof stay unchanged.

Twenty-three focused tests cover the thirteen baseline cases, drift during five stages, mutation between async dispatch and worker entry, revocation/untrusted stops, and allowed capacity-stop/enabled-state transitions. Account/event/outbox snapshots and journal hashes verify that initial refusal adds no new records. Scheduler tests return UNKNOWN and do not fabricate VERIFIED_FLAT. Separate synthetic TP/partial-fill end-to-end tests must still complete the actual original full proof and refuse duplicate confirmation. Their raw diagnostics include binding_rejections.

Lifecycle startup holds are accelerated, observation is 0.8 seconds, and request-weight timing is real. These are not new 300-second natural observations or actual exchange measurements. Docker smoke checks the budget-context gate with real SQLite and no network/coordinator/order bridge; separate integrations test coordinator phases and PostgreSQL. Worker draining can still delay cancellation until an original operation returns; no whole-function hard wall timeout is claimed.

Actual account order usage, external IP capacity and complete request-cost bounds remain unproven. Default production execution stays disabled. No Windows installation/database change, real exchange request/order or trading resume occurs in this review.
