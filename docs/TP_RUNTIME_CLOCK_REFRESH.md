# SDK clock rejection stops owned proof admission — synthetic review

The previous proof-freshness gate correctly deferred stale observations, but the clock refresh crossed two validators. The HTTP budget accepted a normal weight header before DemoClient.sync_clock decoded and validated the time sample. A rejected time body, invalid JSON, wrong shape, boolean time, excessive offset or excessive round trip could therefore leave a fresh header in the budget. Six synthetic before-fix cases reproduce that state. The original SDK still rejected the clock response; these tests do not demonstrate an actual signed request, order or weight overrun.

RuntimeBoundClient now clears synced_at and clock_sample on any failed clock refresh and invokes its owned budget's failure callback. This latches untrusted/stopped for the session under its lifetime lock. The original exception is re-raised. The first budget stop reason is preserved, including transport uncertainty and venue throttling. A received weight observation remains historical diagnostic data; untrusted prevents it from admitting a proof. There is no reset/retry path and no new transport call or persistent write in this callback. Settings/transport binding checks continue before refresh.

This changes neither the installed DemoClient nor the historical budget. It applies only to the explicitly assembled synthetic runtime. The successful path still uses the original SDK clock/RTT/offset validation, immutable query rules and budgeted transport. The runtime clone does not modify the source client's clock state.

The same reentrant lifetime lock covers the entire SDK clock refresh through response validation. A concurrent proof check cannot observe the intermediate header while validation is pending. A seventh before-fix test reproduces this race against the initial failure-latch implementation; the final lock correction makes the waiting proof see the stop. The lock is acquired before transport, matching request admission; nested budget calls reuse it in the same thread. Session close also waits for this validation to finish.

Known and uncertain outcomes stay distinct. A completed HTTP response with a rejected clock body retains its normal completed shared weight record and does not manufacture a pending send or poison other cooperating writers. Lost transport responses and 418/429 retain their existing pending/stopped shared state. Neither case refunds or clears historical attempts or order UNKNOWN records. An operator call after a latched failure does not reopen the session.

Thirteen focused tests cover six original failures, success, existing confirmation-loop refresh after a mid-proof freshness deferral (fresh and stale initial metadata), and three refresh failures in that loop. Loop scheduling tests deliberately stop at a sentinel before the real proof; they never fabricate VERIFIED_FLAT. The original physical-position read, SDK clock validation and WATCH context are exercised. The separate unmodified TP/partial-fill end-to-end tests still require the actual original full-flat proof.

Full regression, static analysis and network-none Docker smoke accompany this source. Docker tests only a client, gate and real local SQLite journal, without an order bridge or PostgreSQL; separate integration tests cover those protocols. Lifecycle startup holds are accelerated, observation is 0.8 seconds and request-weight timing is real. These are not new 300-second observations or exchange measurements.

Actual account order usage, external IP capacity and complete request-cost bounds remain unproven. Production execution stays disabled. No Windows installation/database change, actual exchange request or real order is performed.
