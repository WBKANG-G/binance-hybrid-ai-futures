# 과거 요청 보존과 실행 구조 변경 검토 — 2026-11-13

현재 상태 확인을 마쳤지만 기존 실행 조립기를 그대로 재개할 수는 없다. 과거 요청 표시와 별개로 비용 모델이 34건의 전체 이력을 매번 조회하므로 단일 요청 창의 한도를 초과한다. 또한 이 조립기는 합성 전송을 명시적으로 선택한 테스트용이며 기본 경로와 기본 실제 전송을 거부한다. 이 관리형 실행 경로의 DEMO 운영 어댑터와 입장 검증을 별도로 구현해야 한다. `allow_synthetic_model_execution`을 켜는 것은 운영 DEMO 승인 절차가 아니다.

## 이번 단계의 결과

새 오프라인 검토 코드 `services/execution/demo_history_coverage_candidate.py`는 원본 이력 집합과 실시간 조회/보관 후보 집합이 정확히 일치하는지 검사한다. 누락·중복·중첩·미등록 참조는 거부한다. 보관 후보가 있으면 비용 계산상 들어맞더라도 미구현 증거 검증 권한 때문에 보관 채택을 거부한다. 현재 런타임은 계속 전체 34건을 사용하며 새 검토 코드를 호출하지 않는다.

실제 기록은 읽거나 변경하지 않는다. JSON 보고서의 요청 분류와 건수는 사용자가 제공한 화면을 옮긴 관측 요약이며 새 검증이 아니다. 참조 값은 모두 합성 자리표시자다. 저장된 UNKNOWN/SUBMITTING은 그대로이고, 해소·보관·실행 승인은 모두 false다.

## 확인한 사실과 처리 정책

- 진입 2건: 원격 FILLED 관측과 로컬 CLOSED 이력이 있다. 요청 표시 UNKNOWN은 보존하며 정식 대조 전 임의로 FILLED/ACKNOWLEDGED로 쓰지 않는다.
- 손절 UNKNOWN과 종료 SUBMITTING: 체결 0으로 취소된 동일한 진입 주문의 노출 정정 영수증과 연결된다. 정정은 로컬 노출·위험액·포지션 상태만 바꾸고 요청 상태를 보존하도록 구현돼 있다. 이를 미전송·취소의 독립적인 원격 증명으로 승격하지 않는다.
- 여러 계정 수준 비상 상태 해제 확인은 개별 요청 결과 증명이 아니다.
- 개별 원래 ID 조회의 “찾을 수 없음”은 유지한다. 과거 요청을 무조건 다시 보내거나 전체 동일 조회를 반복하지 않는다.

현재 원격 관측 본문 해시는 비공개 결과 파일에 있고 기존 감사 체인은 본문을 직접 바인딩하지 않는다. 새로운 보관 증거 권한을 구현해도 이 파일을 소급해 독립 증명으로 만들 수 없다.

## 용량의 구조적 한계

| 기존 모델 | 이력 34건 | 동일 가정의 경계 |
|---|---:|---:|
| 증명 작업 및 예약 | 27,366 | 이력 최대 5건까지 적합 |
| 진입 작업 및 예약 | 5,920 | 이력 최대 29건까지 적합 |
| 두 작업 모두 | 가용 5,700 초과 | 이력 최대 5건 |

증명 식은 `(6+h) * (406+6h) + 80*(h+1) + 38 + 128`이다. 이력 수에 따라 이차적으로 증가한다. 이력 5건에서는 증명 5,442가 들어가지만 6건에서는 6,030으로 초과한다. 기다리거나 계정 요청 압력이 0이 되어도 단일 작업 자체가 들어가지 않는다. 현재 한도는 가정이며 실제 거래소/IP 사용량을 검증한 값은 아니다.

34건 중 29건을 별도 검증 가능한 보관 증거로 대조하고 실시간 조회 대상 5건만 남기는 **새 프로토콜을 가정하면** 계산상 들어갈 수 있다. 이것은 구현되지 않은 가정이며, 현재 채택된 증명서는 0건이다. 기존 프로필의 이력 수를 5로 바꾸거나 주문 29건을 삭제하는 변경은 하지 않았다. 새 정책의 전체 이력 포함 관계와 종결 증거 검증이 먼저 필요하다.

## 구현 순서와 통과 조건

1. **응답 증거의 원자적 결합**: 정규화한 요청 식별·범위·본문 해시/원본 참조를 해당 FINISH 감사 이벤트와 독립 체크포인트에 원자적으로 결합한다. 기존 감사 행은 변경하지 않는다. 응답 이후 커밋 실패·응답 불명·재시작·동시 작성 시 보류/중단하며 재전송하지 않는다. 이 단계 자체가 원격 계정 식별을 증명하는 것은 아니다.
2. **과거 불확실성과 종결 증거의 구분**: 원격 종결을 확인할 수 없는 과거 요청은 원래 상태와 근거를 별도로 보존한다. 보관을 위한 운영자 확인이 필요해도 그것을 실제 취소·미전송 증명이라고 표시하지 않는다. 이전의 계정 수준 확인을 새로운 보관 승인으로 재사용하지 않는다.
3. **검증 가능한 종결 증명서**: 계정 범위, 원본 주문·체결·보호 주문·종료 관계, 증거와 버전, 위변조 방지, 취소 후 추가 체결 등을 검증한다. 원문은 보존하고 별도 인덱스/증명서를 사용한다. 해시 문자열만 있거나 모든 참/거짓 표시를 입력했다고 권한을 주지 않는다.
4. **이력 포함 관계와 새 비용 모델**: 모든 원본 주문이 실시간 조회 또는 검증된 보관 증거에 정확히 한 번 포함돼야 한다. 보관 증거는 매번 로컬에서 검증하고 현재 전역 포지션·일반/알고 주문·잔여 위험·새 사건은 신선한 조회로 대조한다. 새/기존 이력이 늘어도 동작하는 정상·장애 경로를 독립 비용 추적으로 검증한다. 증명 작업의 무검토 분할이나 만료된 스냅샷 재사용은 허용하지 않는다.
5. **관리형 운영 DEMO 어댑터와 재입장**: 기본 실행 거부를 유지한 새 운영 경로를 구현하고 독립 계정 범위, 계정 전체 주문 사용량, 실제 요청 압력과 공유 IP 관리, 원가 계약, 기간·위험·리더·저장소·정합성·보호 주문 게이트를 검증한다. 증명서 29건이나 단일 모델 적합성만으로 입장을 승인하지 않는다.

한 번 과거를 분리해 빈 이력으로 시작하는 것만으로는 장기 문제가 해결되지 않는다. 새로운 종료 주문도 검증 가능한 증거로 지속 관리해야 한다. 현재 한도·headroom·10페이지·4회 정리 가정과 기존 보호 조건을 약화시키지 않는다.

## 이번 단계에서 하지 않은 일

DB·파일·요청 상태·원본 이력·실행 프로필·주문 권한은 변경하지 않았다. Windows에서 추가 실행할 명령은 없다. 위험한도 변경이나 자동 재개·실거래 활성화도 하지 않는다. 다음 코드 구현 대상은 첫 번째 항목인 원자적 요청/응답 증거 결합이다.
