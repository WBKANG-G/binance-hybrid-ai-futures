# GET 증거 연결 후보와 시계 변경 정책 검토

2026-11-14 사용자가 실행한 기존 Windows 이미지 검토는 기준 파일 89개, 후보 2개, 기본 거부 5개를 확인했다. 설치·스키마 생성·바인딩·원본 및 복구 사본 시작은 없었다. 이번 변경은 그 뒤의 개발 환경 검증 단계이며, 수정된 후보와 새 연결 모듈이 Windows에 적용됐다는 의미가 아니다.

`services/execution/demo_response_evidence_bootstrap.py`에 기본 읽기 전용 계획과 명시적 적용 함수를 추가했다. 적용은 별도의 `apply=True`, `readers_stopped=True`가 필요하다. writer 정지는 운영자 확인이며 독립 검증으로 표시하지 않는다. Windows 실행기나 자동 설치 경로는 추가하지 않았다.

연결 전에는 계좌 공유 잠금, 기존 전역 스키마 잠금, PG scope 잠금, SQLite 잠금 순서로 검사한다. DEMO·일시 정지·NORMAL·로컬 노출 없음·활성 소유자 없음·계좌 저장소 바인딩·설치 ID·현재 기간 키·기존 V1 감사 기록과 복구 증거를 확인한다. 시작 대기와 미완료 요청 검사도 통과해야 한다. 계획은 테이블이나 확인 파일을 만들지 않는다.

적용은 V2 보조 테이블·불변 트리거·기존 감사 tip에 대한 바인딩만 같은 PG 트랜잭션에 기록한다. 기존 감사 행을 소급 채우지 않는다. 계좌·재무 이벤트·outbox·일/주 기준·기존 SQLite 저널·리소스 체크포인트는 변경하지 않는다. 독립 파일 확인 증거는 새 파일로 fsync한다. 이미 완전히 일치하는 바인딩은 검증만 한다.

PG와 파일을 하나의 원자적 트랜잭션으로 묶었다고 주장하지 않는다. 파일 생성 전 오류는 PG 스키마와 바인딩을 롤백한다. 파일 생성 뒤 오류나 PG commit 실패에서는 확인 파일이 남을 수 있다. 다음 검사에서 orphan/gap을 거부하며 파일 삭제·수정·재생성·자동 재시도를 하지 않는다. 성공 반환이 없는 결과는 수동 증거 검토 대상으로 남긴다. 계좌 잠금은 scope 트랜잭션 종료까지 유지된다.

동일한 호스트 부팅 안에서의 프로세스 재시작은 동일 바인딩과 감사/확인 파일이 일치하고, 단조 시간이 후퇴하지 않으며, 벽시계와 단조 시간의 차이가 기존 허용치 1초 이내일 때만 재검증할 수 있다. 다른 boot ID, 시간 후퇴, 1초 초과 drift, NaN·무한대·비 UTC 시간은 차단한다. V2 저널은 변경된 시계를 쓰기 전에 먼저 검사한다. 실행 중 표본 사이에 장애가 생겨 기존 저널과 PG 사이 불일치가 생겨도 체크포인트 검증이 재개를 막는다. 부팅 변경 뒤 70초를 기다렸다는 이유만으로 통과하지 않는다. V2에는 `CLOCK_REBASE` 기록을 자동 합성하는 기능이 없다.

실제 Windows 원본의 마지막 확인 일자는 2026-11-13이다. 현재 일자와의 불일치나 호스트 부팅 변경이 남아 있으면 이 후보도 중단해야 한다. 날짜 자동 채택, 기존 기록 초기화, 과거 요청 재전송으로 해결하지 않는다. 보존된 미해결 요청 4개도 해소됐다고 표시하지 않는다.

개발 환경에서 실제 PostgreSQL·SQLite·독립 파일을 사용한 기존 및 신규 테스트 94개와, 네트워크 없는 기준 API 이미지에서 새 연결 모듈까지 메모리 import한 검사 1개가 통과했다. 이미지 검사에서는 기준 파일 89개, 후보 3개, 거부 6개와 네트워크·DB·파일 쓰기 시도 0회를 확인했다. lint와 두 변경 소스 파일의 타입 검사도 통과했다. 거래소 응답은 합성이며 Windows의 새 설치, 실제 GET 또는 별도 PC 검증은 수행하지 않았다. 상세 명령과 범위는 `GET_BOOTSTRAP_VALIDATION.json`에 기록했다.

다음 검토는 V2 전체 테이블·함수·트리거를 포함한 스냅샷과 쓰기 경계다. 현재 원본과 복구 사본은 계속 정지 상태로 유지하고 분리된 USB는 별도 보관한다. 설치 준비, 원격 계좌 정체성, 계좌 전체 주문 사용량, 실제 IP 용량, 요청 비용 상한, 전체 재무 증명, 실행 승인은 여전히 확인되지 않았다.
