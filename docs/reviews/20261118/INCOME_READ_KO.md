# 현재 일·주 USDT 자금 내역 수집과 지갑잔고 후보

사용자의 다음 단계 지시에 따라 고객지원 없이 사용할 수 있는 일반 GET 수집기를 준비한다.
앞선 저장 응답의 Windows 재분석 결과는 일반 주문 3건(취소 1, 매수 체결 1, 매도 체결 1),
알고 0건, 원래 종료/손절 ID 일치 0건이었다. 그 결과로 두 요청을 해소하지 않는다.
시장가 주문의 price=0은 실행 가격 0을 뜻하지 않으며 자금 계산에 해당 필드를 쓰지 않는다.

## 수집 범위

과거 고정 백업에서 주간 시작 요일과 기존 진입 2건의 대조 기준을 읽는다. 현재 서버 시각으로
KST 일/주 경계를 정하고, week boundary부터 첫 잔고 응답 직후 고정한 cutoff까지
/fapi/v1/income의 모든 자산/유형을 조회한다. symbol·incomeType 필터로 다른 활동을 숨기지 않는다.
현재 범위의 지갑잔고 후보를 위한 자료이며, 과거 11월 13일이나 최초 지급 근거를 확보한 것은 아니다.

/fapi/v3/account의 전후 원문, income의 최대 3페이지(각 1000), 수집 구간의 별도 income,
시각 창과 영수증을 새 보호 NTFS 디렉터리에 보관한다. 첫 잔고 요청 시작~둘째 잔고 응답
종료까지의 자금 흐름이 하나라도 있으면 역산 후보를 내지 않는다. cutoff는 서버 시각 기반의
클라이언트 추정이며 계정 응답의 독립 원자적 평가 시각이라고 주장하지 않는다.

최대 HTTP 10회, income 페이지는 3개까지다. 1000행은 다음 페이지를 요구하며 진전이 없거나
3페이지 모두 포화면 불완전으로 중단한다. 문서화된 가중치는 income=30, account=5이며
사전 여유 300을 요구한다. 현재 분당 REQUEST_WEIGHT 한도/사용량을 읽되 외부 IP 사용과
월간 내보내기 횟수를 알거나 통제한다고 주장하지 않는다. 내보내기 생성은 전혀 없다.

## 합산 및 후보의 한계

incomeType+tranId로 중복 제거한다. 동일 재정 필드의 재등장은 한 번만 합산하고,
금액/자산/시각/종목의 충돌은 거부한다. 서로 다른 유형의 같은 tranId는 별개 거래다.
금액은 고정 소수 문자열, 최대 정수부 12자리·소수 8자리만 Decimal로 처리한다.
최대 3000행의 합산에서도 Decimal 유효 범위를 넘지 않는 입력 한도를 사용한다.

USDT income의 순합만 USDT 지갑잔고에서 역산한다. USDC/BTC를 합산/환산하지 않는다.
별도 체결표의 손익·수수료를 다시 더하거나 빼지 않으며 ledger.realized의 과거 잔고 차이를
거래소 실현손익 합계로 재사용하지 않는다. 미검토 USDT 유형은 OTHER_UNREVIEWED로
집계하되 후보 생성을 보류한다. KST 경계 밀리초에 이벤트가 있으면 그 경계 후보도 보류한다.

전후 잔고 동일·수집 사이 income 없음·페이지 종료·검토된 유형을 충족해도 지갑잔고 후보다.
해당 자정의 포지션/평가손익, 거래소 보관과 반영 지연, 자금 충전/초기화 기록의 완전성을
독립 증명하지 않았다. 계좌 평가액 기준금액과 고점·손실한도는 채택하거나 초기화하지 않는다.
현재 스냅샷의 포지션 0을 과거 자정의 포지션 0으로 승격하지 않는다.

## 보존/개인정보 경계

고정 데모 호스트·GET 전용·TLS 검증·리디렉션 금지·자동 재시도 금지를 재사용한다.
키는 로컬 숨김 입력과 프로세스 메모리에서만 사용하고 파일/환경변수/명령줄에 저장하지 않는다.
응답은 스키마 검사 전에 저장·해시 대조한다. 콘솔에는 원문 ID/임의 유형/원래 응답을 출력하지 않는다.
기존 원본/복사본/DB/시도 guard는 읽거나 변경하지 않는다. 원본/복사본 정지와 USB 분리를 유지한다.
실제 Windows API 성공은 실행 화면으로 확인할 때까지 미관측이다.
