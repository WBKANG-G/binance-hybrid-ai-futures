# 16일자 Windows 합성 private-tmpfs·복사본 검토 패키지

이 단계는 15일자 합성 증거 검토 이후의 Windows 실행 패키지를 준비한다. 원본 컨테이너와 기존 복구 사본은 정지 상태, USB는 분리 보관 상태로 유지한다. 실제 키 입력·거래소 HTTP·주문·기준금액 채택은 포함하지 않는다. 이전 ZIP을 수정하지 않는다.

15일 증거 영수증은 사용자가 보낸 성공 화면과 읽기 전용 검사 화면에서 일치한 64자리 해시 `0dc12ec08a82e708d31ce90e1846228016c5120a0ec24517ad282ab81eabe37e`로 고정했다. 이는 사용자 텍스트나 외부 독립 보관 증명이 아니다. 그 이전 시계 영수증은 사용자가 텍스트로 제공한 `8bd24518a93cb977479dbcaed2670236c256386ac400e9b129f35965a167d6f5`로 고정한다. 실행기는 고정 해시와 기존 계보·내용 객체·미해결 요청·정지 컨테이너·볼륨 및 마운트를 검사한다.

한국 날짜 16일만 허용한다. 새 자원 생성 전에 호스트 날짜를 검사하고 새 helper에서도 다시 검사한다. 70초 이상의 시계 대기를 마친 뒤에만 75초 키 lease를 연다. 현재 일간·주간 키는 16일/16일이지만 저장 키 13일/9일은 바꾸지 않는다. 검토 도중 날짜가 바뀌면 성공으로 보고하지 않는다.

기존 보존 원시 파일에서 새 PostgreSQL·runtime·소켓 볼륨을 만들고 새 네트워크 없는 DB만 시작한다. Python 후보 15개는 RAM에서 로드하며 이미지의 기준 파일 89개를 먼저 해시 비교한다. 키 등록·holder·읽기 helper는 별도의 project, UID 10001, 읽기 전용 root, cap drop ALL, no-new-privileges, network none, restart no, log driver none으로 생성한다. 키용 named tmpfs도 매번 새 UUID를 사용한다. 실제 키 입력이나 환경 변수 fallback 없이 코드에 정한 합성 pair만 등록한다.

등록 helper에는 키 볼륨 RW만 연결한다. holder와 읽기 helper의 키 마운트는 RO다. 읽기 helper에는 새 runtime RW와 새 Unix socket RO만 추가한다. 원본/기존 복사본 ID·볼륨과 새 DB 데이터 볼륨은 private helper의 허용 집합에서 제외한다. 생성 시 전체 inspect 자료로 Python 정책을 검사하고, 실행 전후 변경 불가 보안·마운트 필드를 재비교한다. 저장한 생성 시 자료는 launcher의 로컬 관측이며 외부 독립 attestation으로 표현하지 않는다.

합성 서명/원문 보관/내용 검사를 한 번 마친 뒤 모든 새 키 helper를 정지한다. 마지막 tmpfs unmount 뒤 key-only registrar를 빈 디렉터리 확인 용도로만 재시작해 실제 키 파일 소멸을 검사하고 다시 정지한다. 이 확인은 날짜 변경 후에도 정리 목적으로 허용된다. 실패 시에도 각 소유 helper의 정지를 모두 시도하고, 전체 정지가 확인되지 않으면 소멸 성공을 주장하지 않는다. 새 PostgreSQL은 별도 정상 정지 확인을 거친다. 자동 재시도·원본 시작·자원 삭제는 하지 않으며 생성 ID와 실패 위치를 보존한다.

합성 파이프라인의 감사 이벤트 2개와 체크포인트·runtime 보관 파일은 새 복사본에서만 변경한다. 원장·기간·기존 자료·34개 주문·4개 미해결 요청은 보존한다. 중첩 JSON은 콘솔과 저장 영수증 모두 객체로 유지한다. 원격 신원·전체 이력·자정 평가·증거 수락·기간 채택·설치 준비·실행 승인은 false다.

검증 기록은 PRIVATE_WEEK_PACKAGE_VALIDATION.json 및 PRIVATE_WEEK_PACKAGE_DOCKER_VALIDATION.json에 기록한다. 실제 Docker 통합은 새 합성 자료를 보존 원시 파일로 만든 뒤 복구하는 전체 PowerShell 경로를 사용한다. Linux에서 Windows ACL과 입력 파일 발견만 대체하므로 실제 사용자 Windows ACL·파일·외부 독립 검증을 증명하지 않는다. 호스트 swap/메모리 스냅샷 보호도 보장하지 않는다. 사용자 Windows 실행 결과는 패키지 전달 후 별도로 확인해야 한다.

최종 ZIP으로 네이티브 검사 38개(20.42초), 새 합성 Docker 보존·복구·private 키 파이프라인 전체 경로 1개(391.52초)가 통과했다. Docker fixture는 시계 감사 0→1, 합성 조회 1→3이며 사용자의 55→56→58 이력을 대체하지 않는다. 합성 키를 등록한 실제 tmpfs가 모든 holder 정지 후 빈 상태로 다시 열리는지 별도 시험에서도 확인했다. 테스트에 사용한 실제 코드와 최종 ZIP을 바이트 비교했으며, 차이는 Linux용 ACL/입력 경로 대체의 extension 끝부분과 합성 입력 영수증·컨테이너 pin뿐이다. 명령 프롬프트 CMD 자체는 Linux에서 실행하지 못하며 PowerShell Legacy 경로를 검사했다.

검증 중 자원 기록의 동일 이름 CreateNew 충돌과 Docker stop --time의 사용 중단 문구가 출력에 추가되는 문제를 발견했다. 순번별 불변 기록 및 별도 최종 기록, 소유 ID에 한정된 SIGINT/필요 시 SIGKILL과 재검사로 수정했다. 실패 자료는 성공으로 취급하지 않았으며 새 합성 자료로 전체 시험을 다시 통과했다. 34개 주문·4개 미해결 요청·저장 13일/9일 키는 유지됐고 새 DB는 정상 정지했다. 실제 Windows 실행은 아직 관측하지 않았다.
