# 고객지원 없이 가능한 복구 경로 조사

2026-11-17 KST 기준 조사다. 기존 백업과 미확정 요청은 보존한다. 이 문서는 대안을
찾아보라는 사용자 요청에 대한 조사 결과이며, 거래·초기화·원장 해소 승인이나 API
실행 결과가 아니다. 고객지원은 유일하거나 필수인 경로가 아니다.

## 우선 경로: 거래소 원문 내역 확보 후 재구성

개별 client ID 조회는 이미 과거 보고서에 NOT_FOUND_UNRESOLVED로 남아 있다.
이를 그대로 반복하는 대신 자료 종류를 바꾼다. 공식 SDK에서 다음 경로를 확인했다.

| 자료 | 공식 SDK에서 확인한 경로 | 무엇을 확인할 수 있는가 | 한계 |
|---|---|---|---|
| 일반 주문 이력 | GET /fapi/v1/allOrders | 원래 clientOrderId와 서버 주문번호·상태 연결 | 개별 조회와 보관 제한을 공유; 없는 결과로 미전송 확정 불가 |
| 알고 주문 이력 | GET /fapi/v1/allAlgoOrders | 원래 clientAlgoId와 알고 주문번호·상태 연결 | 같은 보관 제한; 일반 주문 목록으로 대체 불가 |
| 체결 | GET /fapi/v1/userTrades | 실제 체결·주문번호·수량·수수료 | 비슷한 시간/가격/수량만으로 원래 요청 연결 불가 |
| 수익/자금 흐름 | GET /fapi/v1/income | 자금 이동·실현손익·수수료·펀딩 등의 대조 | 누락·초기화·자산·전체 구간 완전성 확인 필요 |
| 주문 전체 다운로드 작업 | GET /fapi/v1/order/asyn | 개별 조회와 다른 내보내기 자료 확보 후보 | 데모 지원 및 원래 client ID 포함 여부 미확인 |
| 체결 전체 다운로드 작업 | GET /fapi/v1/trade/asyn | 계정 전체 체결 범위·다른 종목 활동 확인 후보 | 데모 지원 미확인; 거래 없음만으로 요청 미접수 판정 불가 |
| 자금 흐름 다운로드 작업 | GET /fapi/v1/income/asyn | 기준시점 이후 USDT 변동 재구성 후보 | 데모 지원·모든 충전/초기화 기록 포함 여부 미확인 |

공식 SDK 주석은 일반/알고 조회에 대해 미체결 CANCELED/EXPIRED 생성 후 3일 경과,
또는 생성 후 90일 경과 주문을 찾지 못할 수 있다고 명시한다. 따라서 과거의
NOT_FOUND는 곧 미전송이라는 뜻이 아니다. 실제 사용자 데모 UI에서는 오래된 취소
주문이 보였으므로 SDK의 문서화된 보관 정책을 데모의 실제 정책으로 단정하지 않는다.
일반/알고 전체 목록도 같은 제한을 명시하므로 이 목록이 삭제된 주문을 반드시
되살린다고 안내하지 않는다. 체결/수익 조회 주석은 최근 3개월, 체결 조회 구간은
7일 이하로 명시한다. 현재 조회 일자에 따라 범위를 다시 정해야 한다.

공식 웹 개발자 문서는 이 환경에서 프록시 CONNECT 403으로 열리지 않았다.
대신 공식 Binance GitHub SDK의 고정 커밋
6a75e7e5744904380ab0bfbd0bd3433b997010f5를 읽었다. 출처 URL·SHA256·정확한
주석·행 번호·9개 메서드의 실제 method/path는 NON_SUPPORT_RECOVERY_SOURCES.json에
기록했다. 이는 SDK 문서 확인이지 실제 데모 API 지원 확인이나 계정 조회가 아니다.

## 최초 지급액을 몰라도 가능한 부분

필요한 기준시점 이후의 전체 잔고 변동을 증명할 수 있다면 현재의 검증된 USDT
지갑잔고에서 그 이후의 순변동을 빼서 당시 지갑잔고를 역산할 수 있다. 최초 지급액을
기억하지 못한다는 사실만으로 모든 일/주 기준금액 재구성이 불가능한 것은 아니다.

- 현재 스냅샷과 과거 기준시점은 UTC 구간으로 명시하고 KST 자정에 대응시킨다.
- 포지션이 해당 자정에도 0이었다는 근거가 있어야 지갑잔고를 평가액으로 사용할 수 있다.
  포지션이 있었다면 그 시점의 평가손익 자료도 필요하다. 현재 포지션 0만으로 대입하지 않는다.
- 전체 USDT 자금 변동을 포함하고, 자산 USDC/BTC를 합산하거나 환산하지 않는다.
- 페이지·구간·계정의 연결, 충전/초기화·입출금·청산·ADL 등의 누락 여부를 확인한다.
- 체결표와 income표의 실현손익/수수료를 중복 차감하지 않는다. 자금표 원문 하나의
  순흐름과 체결 대조를 구분한다. 과거 ledger.realized는 순잔고 차이이므로 별도로 재차
  수수료를 차감하지 않는다.
- 보관 구간 밖·완전성 불명·초기화 기록 누락이면 기준금액을 채택하지 않는다.
- 일/주 기준금액을 재구성해도 최초 지급액·누적 고점·전체 과거 손실한도를 증명한 것은
  아니다. 고점과 기존 위험 중단은 별도 검토하고 자동 초기화하지 않는다.

## 주문 연결의 성공 기준

원래 손절/종료 client ID가 거래소 원문에서 정확히 일치하고, 종목·방향·주문 유형·수량
또는 closePosition 문맥과 최종 상태를 대조해야 한다. 체결된 알고 주문이면 하위 실제
주문/체결과의 명시적 연결도 필요하다. 거래소가 반환한 서버 시각과 자료 출처를 보존한다.
진입 취소, 로컬 CLOSED, 비슷한 가격·시각·수량만으로는 충분하지 않다.
원문에서도 없으면 해당 요청의 역사적 접수 여부는 미확정으로 남는다.

## 기존 도구를 그대로 실행하지 않는 이유

프로젝트에는 과거 trade/asyn 내보내기 코드가 이미 있다. 새로 발견한 완성 도구라고
표현하지 않는다. 현재의 보존 상태에서 그대로 실행할 수 있는지에는 별도 검토가 필요하다.

- services/execution/demo_trade_export.py의 plan은 EMERGENCY와 주문 개수 1~30을
  요구하지만, 보존된 대상 원장은 주문 34개이고 현재 PAUSED/NORMAL 문맥이다.
  이 조건을 맞추려고 원장을 수정하지 않는다.
- 회복용 전송기는 비동기 내보내기 생성 경로를 의도적으로 제외한다.
- GET 이름이어도 asyn은 거래소에 다운로드 작업을 생성하고 월간 쿼터를 소비한다.
  주문/체결/수익 생성은 공식 SDK 기준 각각 월 10/5/100회, 요청 가중치 1000이다.
  일반 조회 전용으로 위장하거나 자동 반복하지 않는다. 생성 시간초과 후 재생성 금지,
  기존 downloadId 상태 조회와 제한된 대기/다운로드 검증이 필요하다.
- 현재 allowlist에는 일부 새 경로가 없다. URL을 바꾸거나 LIVE 호스트로 우회하지 않는다.
- 실제 데모 계정과 키 문맥을 PC의 비공개 경로에서 대조해야 한다. 키 발급 자체가
  새로운 독립 계정을 만드는 것은 아니다. API 키/Secret은 채팅에 요구하지 않는다.

따라서 권장 순서는 기존 기록 보존 → 현재 데모에서 지원되는 공식 내보내기/조회 경로
확인 → 원문 자료 수집 → 오프라인 대조와 부족 범위 표시 → 채택 가능한 부분만 별도
검토다. 조회기 준비와 재개 승인을 분리한다. 이번 조사에서 실제 요청·자격 증명 접근·
다운로드 작업 생성·원장 변경·고객지원 발송은 모두 하지 않았다.

## 원문을 확보할 수 없을 때의 대안

기존 계정의 정확한 역사적 요청을 로컬에서 추론해 확정하는 방법은 찾지 못했다.
하지만 이것이 모든 개발·데모 실험을 영구 중단해야 한다는 뜻은 아니다.

1. 기존 계정을 유지하며 조회·분석만 계속하고, 과거 미확정 요청을 보존한다.
2. PAPER 환경에서 개발을 계속한다. 거래소 계정이나 고객지원이 필요 없으며
   실제 거래소 복구를 완료했다고 취급하지 않는다.
3. 거래소가 지원하는 독립된 새 DEMO 환경을 확보할 수 있다면 과거와 분리된 새 실험을
   시작하는 방안을 별도로 설계할 수 있다. 실제 분리된 거래소 계정/환경 여부와
   최초 스냅샷·자금 내역·일/주·고점 기준, 동일 계정 중복 writer 방지를 검증해야 한다.
   새 API 키, 로컬 account_id나 DB만 바꾸는 방법은 독립 환경을 증명하지 못한다.
   같은 계정의 잔고/원장을 초기화해 과거 손실한도를 우회하는 방법은 권장하지 않는다.
   이 대안은 기존 계정의 복구가 아니며 이번 조사에서 계정 생성/초기화는 수행하지 않았다.
