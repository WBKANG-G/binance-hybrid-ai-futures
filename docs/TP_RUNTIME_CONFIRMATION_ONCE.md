# One confirmation scheduler owner per runtime

The preceding start-deadline scheduler bounded one invocation, but a second invocation constructed a fresh 120-second window and reset the completed/deferral counters. Concurrent invocations could run independent loops against the same coordinator. Seven before-fix scheduler tests reproduce repeated starts after attempts/deadline/deferral exhaustion, operation failure and cancellation, a simultaneous call, and another deadline-clock read. These tests return UNKNOWN and do not fabricate a signed flat proof.

RuntimeConfirmationCoordinator now claims ownership atomically before any deadline read, lease renewal, wait or proof phase. A threading lock protects only the small ownership transition, so it works across threads/event loops without holding a lock during await or HTTP. The first owner runs the existing bounded scheduler. Every later call returns UNKNOWN immediately, including while the owner is still active. It neither waits for nor cancels the owner, starts another window, changes its counters/reason, nor reads another clock.

The claim remains consumed after success, UNKNOWN, exception or caller cancellation. The owner still rethrows original errors/cancellation and keeps its first outcome. A repeated call never returns a cached VERIFIED_FLAT as fresh evidence. A genuine proof already produced by the first owner and any committed quota seal remain intact; rejecting a later call does not invalidate or redo that historical proof. There is no reset/retry API.

This is object-local ownership of the budgeted confirmation entry point. It is not a durable account-wide counter, process lock, IP reservation, or a new restriction on all inherited internal proof methods. The existing fenced ledger, durable order/shared journals, pending-flow checks and runtime single-use guard retain their separate roles. Opening a different runtime still requires the original validations; no missing or UNKNOWN record is repaired or cleared here.

The diagnostic reports whether this scheduler call started/is active and the number of refused calls. Inactive means the awaiting call ended, not proof that a canceled thread stopped. Already-started worker work is not forcibly canceled; the permanently consumed claim prevents a replacement loop while such work may still finish. The prior distinction between a start deadline and a hard wall timeout remains unchanged.

Focused tests cover seven original failures, completion without permission reset, a 16-thread ownership race, and independent ownership objects. Existing deadline/cancellation tests remain in force. Actual synthetic TP and partial-fill lifecycle tests additionally call the entry point again after their original full proof: the repeat must return UNKNOWN with no new trace rows, while the original VERIFIED_FLAT result remains preserved. Their diagnostics must record exactly one refused repeat. No synthetic success is substituted for the original financial proof.

Lifecycle startup holds are accelerated, observation is 0.8 seconds, and request-weight timing is real. These are not new 300-second natural observations or actual exchange measurements. Docker smoke checks the threaded claim/imports/default refusal without network, not the complete financial protocol.

Canonical CLI and installed historical source files are unchanged. Actual account order usage, external IP capacity and complete request-cost upper bounds remain unproven. Default production execution stays disabled. No Windows installation/database change, real exchange request/order or trading resume occurs in this review.
