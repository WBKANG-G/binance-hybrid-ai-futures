# Require original order-journal process ownership during confirmation

An unchanged journal object/reference did not imply that its original process lock was still owned. Closing that journal or losing/replacing its lock path could pass the prior context checks and reach more scheduler work. Six before-fix cases reproduce this before confirmation and after a resource wait. They use real local journal files and scheduler stubs returning UNKNOWN; they do not demonstrate an actual unauthorized order, lost venue capacity or successful financial proof.

The existing confirmation context check now reuses DurableOrderQuota.owns_process_lock before later client/budget checks. Its original PID/read-only/descriptor/lock-inode rules apply at the established phase boundaries and worker entry. Loss raises RUNTIME_CONFIRMATION_ORDER_LOCK_REQUIRED before another renewal, refresh or proof phase. No lock is reacquired, no file restored, and no journal record cleared or sealed. The single confirmation claim remains consumed on failure; normal owned cleanup can still close captured resources.

This check is deliberately process ownership, not a new full journal-integrity audit. Database-file corruption while the original process lock remains held still follows the existing journal validation and one-shot risk-reducing exit fallback rules. The guard neither broadens that fallback nor blocks it solely because a different journal-integrity check would fail. Original per-effect fencing, signing, query admission and full-flat proof remain mandatory. No installed historical implementation or exit policy changes.

Three actual isolated PostgreSQL tests change the owner, fence or lease expiry during a resource wait. The next original fenced renewal already rejects each change; this behavior was retained rather than replaced. Tests compare account/event/outbox snapshots after injected leader loss and retain an unsealed six-slot reservation, without additional heartbeat/proof/seal records. This is evidence for the original database fencing in those cases, not a new account-wide quota proof.

Twelve focused tests cover six lock-loss reproductions, those three PostgreSQL cases, unchanged distinction between database availability and process ownership, preserved precommitted flow after close, and loss between async dispatch and worker entry. Lock-path restoration occurs only in the test harness for fixture cleanup; product code performs none. Scheduler stubs never return VERIFIED_FLAT. Separate TP/partial-fill lifecycle tests must still complete the original signed full-flat proof and retain duplicate-call refusal.

The added guard performs the original local ownership inspection; it does not poll account history, add HTTP requests, query external order usage, refund slots or reset periods. Lifecycle startup holds are accelerated and observation is 0.8 seconds; request-weight timing is real. These are not new 300-second observations or actual exchange measurements.

Docker smoke uses an isolated synthetic guard graph plus a real order journal, without actual coordinator construction, SDK, PostgreSQL or financial proof. It checks closed-lock refusal, unchanged file hash and default execution refusal with network disabled. Full construction and financial behavior have separate integration evidence. Existing worker draining can delay cancellation until work returns; a whole-function hard wall timeout remains unproven.

Actual account order usage, external IP capacity and complete cost upper bounds remain unproven. Default production execution stays disabled. No Windows installation/database change, real exchange request/order or trading resume occurs in this review.
