# Bind offline review results to exact input bytes

The previous CLI emitted a semantic review only. Different raw encodings of the same JSON intentionally produced the same semantic result, and there was no byte binding to distinguish a saved result paired with a different file. The new receipt adds content identification without changing the underlying consistency rules or runtime/financial execution.

The existing CLI now reads one bounded byte buffer and calls review_bytes. A valid status-0/status-3 result includes input_sha256, input_bytes, binding_kind=RAW_INPUT_BYTES_SHA256, receipt_version=1 and a fixed reader_policy. The hash covers exactly the buffer that was parsed and reviewed, including whitespace and ignored fields. The file is not reopened to calculate its hash. Invalid or unreadable inputs still return status 2 without issuing a receipt.

`python -m scripts.review_runtime_confirmation_report REPORT.json --verify-receipt RECEIPT.json` recomputes the complete review from the input, checks policy/version and its raw-byte binding, then compares the complete expected receipt. Receipt JSON key order/whitespace may differ. Other field/type changes, extra receipt fields, false-versus-0 or integer-versus-float substitutions are rejected. A result from another file, even an input with only added whitespace, cannot be used unchanged. Input file paths/names are not part of the binding; identical bytes at different paths are intentionally equivalent and paths are not echoed.

The comparison response is a separate OFFLINE_SYNTHETIC_RECEIPT_COMPARISON_ONLY result, not another issued receipt. Status 0 remains consistent review only; status 3 retains required attention, including seal failure; mismatches are status 2. No output grants execution and next_action stays KEEP_PAUSED_REVIEW_ONLY. The legacy review(data) API remains a semantic review without raw-byte binding. Its output and earlier CLI results are not accepted as new receipts; a receipt must be generated from the original input using the current policy.

Receipts are deterministic and carry no fresh timestamp. A successful comparison proves only that this input buffer and these recomputed result fields match. It does not authenticate the input, receipt, author, source commit, file system state after the read, exchange account or current financial state. Someone who controls both input and receipt can regenerate a matching pair; no signature or trust anchor was added. A concurrent file change after reading does not change the already reviewed buffer, and later verification against changed bytes fails. Verification does not reserve capacity, repair records or write a file/database.

The report still has its existing 16-MiB/JSON/trace bounds. Receipt input has a separate 64-KiB cap and reuses strict duplicate/nonfinite/depth checks. Errors contain fixed codes, never private paths, raw input or unknown fields. A successful content comparison still leaves input_authenticity_verified and receipt_authenticity_verified false.

Twenty-eight new tests cover exact/deterministic bytes, mixed inputs, whitespace, result and policy/version mutations, strict types, unknown fields, a regenerated-but-unauthenticated pair, legacy output, parser/size limits, CLI status/redaction and a single-read file-change fixture. The previous 55 reader tests remain applicable. Saved TP/partial/seal-failure reports are extracted from a SHA-verified prior artifact, issued receipts and compared through the real CLI. A changed input and altered approval result are separately refused. New Docker checks the same offline round trips without network or financial execution.

Financial runtime files are unchanged. Original financial reports still originate from source 9283140d588a523a2ee030888bfeba8c77284ec1; the immediate prior reader artifact is commit 995072e3bd0879dcc67a202e0520671786a4d3b9. Prior financial JUnit files are explicitly reused, not counted as freshly executed lifecycles. Source/input/archive hashes accompany replay evidence. Original startup holds were accelerated and observation was 0.8 seconds; these are not new 300-second natural observations or exchange measurements.

Actual account order usage, external IP capacity and complete cost bounds remain unproven. Default production execution remains disabled. No Windows installation/database change, real exchange request/order or trading resume occurs in this review.
