# Closed-order read transport feasibility probe

16 distinct focused cases passed across runs: the existing seven read-only timing cases plus seven comparison cases in a 14-case run (3.49s), and two added CLI safety cases (0.40s). Tests use isolated real PostgreSQL and synthetic exchange transport. The pooled comparison fixture simulates the context's forwarding/restoration; it does not measure real TLS latency or prove production speedup. The actual recovery HTTPS pool component is reused unchanged. Windows performance measurement remains pending.

Cases verify actual read-only transactions and unchanged financial rows, four signed order GETs and two clock calls, exact same canceled unfilled order evidence in both modes, original source restoration, no execution-transport/policy change, abort on a wrong first response without retry, pooled failure restoration, rejection of write-enabled sources and incompatible custom transports, deadline termination before a signed request, account change between samples, required explicit CLI flag and redacted private failure with nonzero status. Strict mypy and Ruff lint/format pass for the probe/source tests. No real account key, exchange order or mail service was used in cloud tests.

The probe records monotonic nanosecond deltas around SDK request/response processing only. SQL and audit interpretation are excluded; clock warm-up is explicit and excluded from per-request samples. Fixed original-then-pooled ordering and two observations per mode are not a randomized benchmark, causal fill diagnosis or latency SLA. The pool is warmed by its clock call; connection preparation effects and RTT variation must be considered. No ratio, execution improvement or fill probability is asserted.

No application source, signal ten-second expiry, quote freshness, price, quantity, risk, lease, lock, order transport or trading mode is modified. The temporary read client is scoped through the closed-order inspector and restored at context exit. Each individual inspector and an additional full before/after account hash guard protect the no-state-change claim. Failure does not silently fall back to a different order, another transport or a new entry.
