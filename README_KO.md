# 6,000 한도에서 완료 불가능한 확인 작업의 시작 차단

기존 경로는 진입 예산은 검사했지만 전체 금융 확인 묶음이 빈 1분 창에도 들어갈 수 있는지는 시작 시 검사하지 않았습니다. 원래 모델은 과거 주문 수 h에 대해 snapshot=400+6(h+1), proof=(6+h)*snapshot+80(h+1)+38입니다. 확인용 안전 여유 128도 필요합니다.

| 과거 주문 | 전체 확인 묶음 | 여유 포함 | 한도 5,700 대비 |
|---|---:|---:|---:|
| 5 | 5,314 | 5,442 | 258 남음 |
| 6 | 5,902 | 6,030 | 330 초과 |

과거 주문 6개이면 진입 자체의 모델 예산은 들어가지만 완료에 필요한 확인은 불가능합니다. 제한 6,000에서 안전 여유 300을 뺀 5,700은 유지합니다. 창이 비어도 들어가지 않는 작업을 기다림·재시도로 해결할 수 없습니다.

새 `require_runtime_capacity`는 관리형 런타임 조립 시 읽기 전용 원장 확인 직후, 두 파일 저장소를 열거나 writer session을 만들기 전에 불가능한 프로필을 거부합니다. 직접 OwnedSharedBudget 구성에도 같은 검사가 적용됩니다. `RuntimeConfirmationCoordinator.proof_batch`와 시작 검사가 같은 순수 계산 함수를 사용합니다. 기존 확인 절차의 스냅샷·과거 주문·페이지·취소·금융 판정은 생략하지 않습니다. 원래 coordinator의 계산과 0..128 모든 이력 수에서 일치하는지 별도로 검사합니다.

진단 `capacity_feasibility`는 빈 창 적합성, 필요 예산, 여유를 표시합니다. 이는 현재 압력·주문 개수 제한·거래 허가를 검사한 결과가 아닙니다. 이후의 기존 공유 예산 예약·응답 헤더·현재성·소유권·안전 종료 검사는 유지됩니다. 이력이 5개 이하라는 이유로 거래가 허가되지 않습니다. 더 큰 안전 여유는 낮추지 않고 공유 정책의 상한도 올리지 않습니다.

수정 전 같은 PostgreSQL 회귀 검사 2개(과거 주문 6개·128개)는 차단하지 못해 실패했습니다. 수정 후에는 원장/event/outbox 및 두 저장소의 전체 바이트가 보존되고 파일 열기·네트워크 호출 없이 거부됩니다. 이력이 많을 때 해결책은 원장 삭제·이력 누락·대기 연장이 아니라 전체 확인 방식을 안전하게 재설계하는 후속 개발입니다.

현재 모델 비용이 실제 거래소의 모든 비용 상한이라는 증명, 실제 계정 전체 주문 사용량, 비협력 외부 IP 트래픽은 별도 미확인 항목입니다. 이 변경은 그 관측 자료를 만들어내지 않습니다. 실제 사용량을 알 수 없는 상태에서 실행 차단을 해제하지 않습니다. production 기본 비활성화, 정지 상태와 기존 Windows 설치본은 유지됩니다.

검증은 합성 HTTP·로컬 WSS·격리 PostgreSQL만 사용합니다. 현재 관리형 실행 경로의 TP·부분 체결·봉인 실패를 새로 실행하며, 별도로 TP의 300초 관찰도 검사합니다. 시작 시 재시작 대기는 가속되고 요청 예산의 시간과 300초 관찰은 실제 단조 시간으로 흐릅니다. 이는 거래소 실측이 아닙니다. 실제 검증 수와 통과 여부는 배포물 VALIDATION.json 및 JUnit에 기록됩니다. 과거 JUnit을 현재 실행 수로 재사용하지 않습니다.

이 자료는 검토용이며 Windows 설치·DB 갱신·실제 거래소 요청·실제 주문·거래 재개는 수행하지 않습니다.

## 장시간 관찰의 공유 예산 대기

새 300초 모의 관찰에서 추가 실패를 재현했습니다. 자체 요청의 독립적인 60초 최고치는 4,235였지만 공유 예산이 보수적으로 보관하는 과거 헤더와 이후 요청을 합산하여 `SHARED_PRESSURE_ADMISSION_BLOCKED`로 중단됐습니다. 이는 실제 거래소 카운터 6,000 초과를 관측한 사건이 아닙니다. 이후 원래 전체 금융 확인은 VERIFIED_FLAT이었으나 최초 시험 결과는 UNKNOWN/NOT_ACCEPTED였습니다. 이 실패를 시험 성공으로 바꾸지 않았고 evidence에 원래 실패 자료를 포함합니다.

`RuntimeObservationCoordinator`는 소유 중인 단일 시험의 로컬 청산 상태가 확인된 경우에만 전체 재조회 직전 예산을 확인합니다. 동일한 전체 조회 예산과 일반 활동의 여유 640이 부족하면 신규 진입을 로컬 정지하고 같은 리스를 갱신하며 기다립니다. 이때 DB 트랜잭션을 열어 둔 채 잠들지 않습니다. 기존 WATCH 경로로 모든 포지션을 10초 주기로 조회하고, 예산 정보가 만료되면 기존 클라이언트와 공유 예약을 거쳐 시간을 갱신합니다. 새 노출·소유권/연결 상실·리스 상실·조회 실패·시간 이상·한 번의 재조회 대기당 120초 시작 기한·120회 대기 제한은 성공으로 처리하지 않습니다.

대기 중에도 기존 요청의 비용과 공유 헤더 관측은 보존됩니다. 예산이 실제 만료되어 원래 조회 묶음이 들어갈 때에만 원래 전체 재조회를 실행합니다. 외부 프로세스가 그 사이 비용을 사용하면 기존 개별 요청별 예약 검사가 다시 차단할 수 있습니다. 묶음 예산을 실제 IP에서 독점 예약했다는 주장은 하지 않습니다. 포지션이 없다는 자원 관측은 금융 증명이 아니며, 원래 금융 청산 확인·페이지 수·스냅샷·봉인 처리는 그대로입니다. 이미 있던 하드 스톱도 해제하지 않습니다.

재현용 작은 검사에서는 실제 공유 저장소에 4,000 비용을 남긴 뒤, 비용을 환급하지 않고 60초 이상 만료를 기다려 전체 조회를 재개합니다. 이 작은 검사의 시계는 가속되며 자연 300초 관찰과 구분합니다. 추가 검사는 신규 노출, 미체결 주문, 소유권 상실, 잘못된 시계, 제한 도달, 기한 이후에 돌아온 예산, 대기 중 연결 교체, 시간 조회 실패를 다룹니다.

120초는 후속 작업을 시작할 수 있는 기한입니다. 이미 시작한 동기 DB/HTTP 작업을 강제로 취소하지 않으며 전체 함수의 최악 지연이나 네트워크 장애 중 정확한 10초 주기를 인증하지 않습니다. 원래 fencing과 각 요청의 기한·중단 규칙은 그대로 적용합니다.

구체적인 통과·실패 수는 VALIDATION.json을 확인하십시오. 검토용 소스 모음이며 설치 프로그램이 아닙니다.
