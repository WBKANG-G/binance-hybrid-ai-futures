# TP income 조회 축소 계약 검토 — 2026-11-07 KST

**현재 관찰된 소량 이력에서는 income 조회를 바꿔도 비용 절감이 없습니다. 운영 전환을 승인하지 않았습니다.** 대량 수수료 이력에서만 일부 절감하는 합성 후보와 반례를 검증했습니다. 실제 TP 주문 테스트를 다시 실행할 근거는 얻지 못했습니다.

사용자 계정은 앞선 실제 확인에서 11월7일 일간 기준 적용 후 NORMAL/일시정지, 기간 일치, 거래소 비어 있음으로 확인됐습니다. 이 검토에서 계정을 다시 조회하거나 DB를 변경하지 않았습니다.

## 기존 비용 검토와 연결

앞선 income 페이지 예산 후보는 최대10페이지와 flat 확인4회를 보수적으로 반영하여 한도6000에서 진입 전에 거부했습니다. 작은 여유로 되돌리면 검증되지 않은 종료 비용을 감추게 됩니다. 실제 필터 비교에서는 24시간 범위12건, COMMISSION8/REALIZED_PNL4, TRANSFER0/WELCOME_BONUS0이었습니다. 전송 풀은 연결 재사용을 개선하지만 IP weight를 줄이지 않습니다.

따라서 이번에는 운영 예산을 줄이지 않고 조회 계약을 별도 오프라인 모듈에서 비교했습니다. `income_contract.py`는 실제 클라이언트·키·DB를 로드하지 않으며 기존 코드가 호출하지 않습니다. 설치 패치와 운영 CLI도 없습니다.

## 비교 방식

두 방식 모두 최초에는 유형 없는 GET을 한 번 사용합니다. 1000건 미만이면 그 응답으로 끝냅니다. 꽉 찬 경우에만 다음과 같이 나눕니다.

- `adaptive_filtered`: TRANSFER와 WELCOME_BONUS를 각각 조회합니다. 각 유형이 다시1000건이면 해당 시간 구간을 나눕니다.
- `unfiltered_split`: 유형 필터 없이 시간 구간을 나눕니다. 필터를 사용하지 않는 대조군입니다.

시간 구간은 `[start,mid]`, `[mid+1,end]`로 나눠 밀리초 경계의 누락·중복을 피합니다. page를 보내지 않으며 조회 시작 시각을 앞으로 이동하거나 오래된 transfer를 버리지 않습니다. 단일 고정 범위는 최대7일, 최대64요청·깊이20·30초로 제한합니다. 한 밀리초도1000건으로 가득 차거나 예산을 초과하면 부분 결과를 성공으로 반환하지 않습니다. 이 제한을 운영 예산에 반영하거나 기존 10페이지 정책을 대체한 것은 아닙니다.

TRANSFER/WELCOME_BONUS의 양수·음수·동일ID의 서로 다른 유형을 기존 위험 회계 대상 그대로 보존합니다. 비USDT 대상, 유한하지 않은 금액, 충돌하는 동일ID, 잘못된 필터·시간 응답, 부모 응답에서 보인 대상의 자식 조회 누락을 차단합니다. 그 외 income 유형을 모두 금융 회계로 분류했다고 표시하지 않습니다.

기존 page 모델 숫자는 서버가 page를 제대로 지원한다는 가정 아래의 계산입니다. 현재 공식 SDK가 page를 노출하지 않는다는 사실만으로 서버가 page를 무시한다고 결론짓지 않습니다. 공식 계약 출처는 CONTRACT_REFERENCE.md/JSON에 있습니다.

9003건의 희소 대상 사례에서는 income 항목만 모델비용300→90으로 줄었습니다. 반대로 1003건과 대상 밀집 사례에서는 늘었습니다. 시간 분할은 전 구간을 읽기 위해 대량 수수료 사례에서31회가 필요했습니다. 이 수치는 TP 전체·청산·보호 확인의 비용 보장이나 실제 weight 절감 증거가 아닙니다. 최대64회에 weight30을 곱한1920도 기존 income10페이지 모델300보다 큽니다. 예산 여유를 낮추는 근거로 사용할 수 없습니다.

## 입증되지 않은 부분

합성 서버의 필터 동작은 실제 DEMO 서버의 동작을 입증하지 않습니다. 최초1000건에 없었던 보너스를 서버가 필터 조회에서 조용히 누락하는 반례도 넣었습니다. 이 경우 클라이언트만으로 누락을 알아낼 수 없습니다. 따라서 반환값은 항상 `server_filter_support_proven=false`, `runtime_switch_approved=false`입니다. 실제로 두 대상 유형을 관찰하지 못한 기존 결과를 긍정 증거로 바꾸지 않았습니다.

이 변경은 현재 한도 초과의 해결책으로 배포하지 않습니다. 현재 계정처럼 income이 한 번에 끝나는 경우에는 반복 스냅샷과 다른 고비용 경로를 줄이는 작업이 더 직접적입니다. 기존 이벤트 묶음 처리·진입 전 예산 후보와 결합하더라도 실제 한도6000에서 종료 여유를 보장한다는 새 증거는 없습니다. 부분체결 보호와 실제 TP 체결 후 원래SL 정리의 승인 증거도 추가되지 않았습니다.
