# TP 요청 예산 후보 구현 — 2026-11-06 (한국시간)

진입 전에 보호 설치·종료 여유를 검사하고, 반복 조회가 종료 몫을 쓰기 전에 관찰을 중단하는 **검토용 후보 코드**입니다. 사용자 Windows, 실제 거래소, 계좌 DB에는 적용하지 않았습니다. 기존 CLI에서는 활성화되지 않으며 설치 명령도 제공하지 않습니다. 실제 계좌의 일시정지는 유지합니다.

## 검증 결과

- 수정 후 단위 테스트 755개 통과(12.50초).
- 기존 경로와 후보의 통합 테스트 161개 통과.
- 서로 다른 실행에서 확보한 총 916개 테스트 통과 증거입니다. 단일 실행의 전체 녹색 결과로 표시하지 않습니다.
- 초기 광범위 실행은 909 통과/3 실패였습니다. 실패는 새 후보 소스를 기존 승인 해시로 검사한 레거시 단위 테스트 3개였습니다. 승인 핀을 수정하지 않고 테스트의 모의 입력 경계를 분리했으며, 변조 입력·실제 후보 차단 검사를 추가한 후 단위 테스트 전체를 다시 통과했습니다. 통합 테스트 중 실패는 없었습니다.
- 전체 코드 Ruff 및 133개 소스 mypy 통과. 변경 8개 파일 format/diff 검사와 기준 소스에 대한 패치 적용·해시 검증 통과.

## 구현 내용

- `TPRequestBudget`: 같은 전송 래퍼를 사용하는 진입 준비·관찰·WSS 관련 요청을 합산합니다. 진입 때 `현재 보수적 사용량 + 진입·보호 가정 비용 + 종료 가정 비용 + 여유분 <= 공개 한도`를 요구합니다. 이후 일반 요청은 종료 몫과 여유분을 제외한 범위에서만 허용합니다.
- 요청 전 원자적으로 가정 비용을 차감하고, 응답 헤더가 더 큰 사용량을 알리면 그 값을 반영합니다. 실패한 전송은 환불하거나 재시도하지 않습니다. 정의하지 않은 경로의 비용을 임의로 작게 취급하지 않습니다.
- 5초 이내의 유효 헤더 없이 진입하지 않습니다. 헤더 누락·비정상 값·전송 예외·실제 418/429 뒤에는 일반 요청을 허용하지 않습니다. 아직 중단되지 않았다면 기존 시계 GET으로 오래된 헤더를 갱신할 수 있습니다.
- 로컬 분 경계나 낮아진 헤더로 예산을 복구하지 않습니다. 이번 후보는 **관찰 1회 전체에 적용하는 비갱신 예산**입니다. 실제 분별 사용량보다 더 일찍 차단할 수 있으며 5분 관찰을 보장하지 않습니다.
- `BudgetedTPTriggerCoordinator`: 기존 capped LONG LIMIT 경로를 상속합니다. 진입 의도를 만들기 전에 예산을 검사하고, private 세션과 작업 스레드가 회수된 뒤에만 종료 단계로 전환합니다. 중단 상태에서는 다시 진입할 수 없습니다.
- 종료 단계에서는 기존 fencing·reduce-only·동일 ID·fresh snapshot·flat 확인·SDK cooldown 절차를 그대로 사용합니다. **로컬 예산 부족을 이유로 원래 위험 감소 요청을 차단하지는 않습니다.** 이는 종료의 절대 성공이나 실제 요청 한도 준수를 보장하지 않습니다. 실제 429 cooldown은 우회하지 않습니다.
- private 세션이 종료 오류를 억제하더라도 예산 중단 상태는 검증 실패로 남깁니다. 실제 flat 증거를 확보해도 중단된 관찰을 TP 검증 성공으로 올리지 않습니다.

기본 coordinator에는 아무 동작도 하지 않는 `begin_finalization` hook만 추가했습니다. 후보 subclass를 구성하지 않은 기존 CLI의 경로·진입 한도·정리 증거는 바꾸지 않았습니다. `TP_REQUEST_BUDGET_STOPPED`는 실제 거래소 rate limit과 구분하는 allowlist 진단입니다.

## 검증에서 확인한 행동

사용자 실측을 참고한 합성 비용 모델, 과거 주문 19개, 공개 분당 한도 6,000에서 **신규 주문 전 차단**을 확인했습니다. 비교한 dual-side 비용 30/35 모두 진입·보호 1,500, 종료 3,000, 여유 300의 가정을 만족하지 못했습니다. 이 숫자는 구현 테스트 입력이며 새로운 운영 설정이나 입증된 비용 상한이 아닙니다.

활성 제어 경로 자체를 검증하기 위해 **실제 한도와 다른 합성 한도 12,000**을 대조군으로 사용했습니다. 이벤트 집중으로 일반 요청을 멈춘 뒤 기존 reduce-only 종료와 flat 확인이 동작하고 기존 이력·위험 기준값이 보존됨을 확인했습니다. 이 대조군은 실제 한도 6,000에서 같은 거래가 가능하다는 증거가 아닙니다. 실제 거래소의 한도를 12,000으로 바꾸는 코드나 제안도 아닙니다.

공유 IP 사용량 급증으로 합성 429를 주입하면 여전히 자동 종료가 막힙니다. 후보는 SDK cooldown을 지키고 노출을 EMERGENCY/UNKNOWN으로 남깁니다. 이 위험은 해결됐다고 주장하지 않습니다. 마지막 listen-key 종료에서만 예산 오류가 나는 별도 대조군도 TP 성공으로 수용하지 않습니다.

세부 실행 수와 시간은 `VALIDATION.json`, 실행 결과는 `test-results/`, 합성 요청 추적은 `synthetic_reports/`에 기록합니다. 테스트 통과에는 의도한 거부·잔존 노출을 정확히 보고하는 사례가 포함됩니다. 통과 개수는 실제 청산 성공 횟수가 아닙니다.

## 배포하지 않는 이유와 다음 구현 조건

인접 응답 카운터 차이는 공유 IP 활동을 포함할 수 있어 엔드포인트 비용의 확정값이 아닙니다. 미측정 경로의 40도 입증된 상한이 아닙니다. 쿼리 옵션·이력 증가·서버의 별도 주문/WSS 한도도 이 모델로 완전히 제한하지 못합니다. 따라서 이번 후보를 실제 주문 승인 장치로 사용하지 않습니다.

운영 적용 전에는 현재 이력을 포함한 진입·보호·정리의 보수적 비용과 요청 수를 검증하고, 기존 flat 증거를 유지하면서 불필요한 반복 조회를 줄이는 설계가 필요합니다. 분별 예산 갱신은 신뢰할 수 있는 서버 분 경계와 응답 순서 증거가 확보된 별도 변경으로 다뤄야 합니다. 현재 설치 승인 해시 목록과 잠금 사양은 변경하지 않았으며, 예전 설치가드는 후보 소스를 DB/서명 조회 전에 거부합니다.

## 재현과 파일 검토

기준 소스는 `e9327bd4729c7b5a4eeebff0e309f0f631395098`입니다. `source.patch`와 `source/`는 같은 변경을 담고 있습니다. 폐기 가능한 클라우드 체크아웃에 기준 소스를 가져온 후 patch를 적용해 비교할 수 있습니다. **사용자 Windows 컨테이너나 실제 DB에는 적용·실행하지 마십시오.**

단위 테스트는 `tests/unit/test_tp_request_budget.py`, 실행 테스트는 `tests/integration/test_tp_request_budget_lifecycle.py`입니다. 후자는 격리 PostgreSQL에만 연결하며 실제 로컬 WebSocket과 합성 REST/시계/주문을 사용합니다. fixture는 이전 `6b03e35c1fab51b4564a6cce56ba7c526fd52e13`의 합성 이력·가중치 모델에서 가져왔습니다. 원본 pytest 설정·의존성을 사용해야 합니다.

레거시 설치가드 단위 테스트의 정상 리뷰 사례는 고정된 모의 소스 입력으로 분리했습니다. 변조된 입력의 DB 이전 차단과, 이번 실제 후보 체크아웃을 기존 승인 핀으로 거부하는 검사를 추가했습니다. 운영 설치가드의 승인 범위를 넓히거나 해시 검사를 제거하지 않았습니다.
