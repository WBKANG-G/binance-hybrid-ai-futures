# DEMO 수동 종료 장부 반영 — 수수료 전사 오류 수정

이전 도구는 제가 매도 수수료를 `0.02119185`에서 `0.02111985`로 잘못 옮겨 `SIGNED_TRADE_PROOF_MISMATCH`로 차단됐습니다. 이전 안내의 수수료 포함 손익도 `−0.07025287`에서 **−0.07032487 USDT**로 정정합니다. 금액 비교를 완화하지 않고 원본 값으로 수정했습니다.

이 검사 실패는 정정 쓰기 단계 전에 발생합니다. 이전 출력의 `application_may_have_completed: true`는 모든 적용 오류에 보수적으로 붙던 값이었습니다. 새 도구는 정정 호출 전/후를 구분하며 DB 임대 기록 가능성을 따로 표시합니다. 기존 실패 실행에서는 임대·fence·감사 기록이 남을 수 있지만 해당 장부 정정은 실행되지 않는 경로입니다.

원본·종료 주문, 체결, SL/TP, 거래소 빈 상태, 손실/날짜/입출금, 원장 일치 검사를 전부 다시 수행합니다. 수수료와 다른 값이 일치하지 않으면 차단하며, 수수료 포함 손익은 검증된 실제 체결 값에서 계산합니다.

대상은 `041d1f35-870e-46cb-aad2-ed6059bc1095` 한 건입니다. 진입 주문 `28668115919`, 수동 종료 주문 `28668119491`, 체결 ID `554837511`/`554838531`, 각각 0.0007 BTC와 사용자가 제공한 가격·수수료·체결 시각을 고정했습니다. 실제 서명 조회에서 매도 종료 주문은 FILLED/MARKET/SELL/BOTH/reduceOnly=true였습니다. 현재 거래소 포지션·일반 주문·Algo 주문도 0으로 확인됐지만 앱 장부에는 아직 미종료 0.0007 BTC가 남아 있습니다.

이 도구는 실행 시 증거를 다시 조회합니다. 정상 종료가 확인된 경우 해당 작업의 장부상 open_quantity·actual_risk를 0, position_state를 CLOSED로 바꾸며 현재 계좌 금융 값을 안정적인 서명 스냅샷으로 갱신합니다. 수수료를 다시 차감하지 않습니다. 일·주 기준금액·기간 키·high-water·입출금·다른 주문·요청 상태·실패 진단·TP 실패 기록은 보존합니다. high-water를 올려야 하는 별도 상황, 기간 변경, 손실 한도 초과 등은 차단합니다.

수동 종료는 operations의 고정 UUID 영수증에 원래 주문과 서명 증거를 별도 기록합니다. 앱의 exit_id/exit_state/exit_generation은 원래 값 그대로입니다. 앱이 DX 청산을 실행했다거나 TP가 체결됐다고 기록하지 않습니다. 원래 실패 이력은 보존하며 NORMAL/진입 일시정지를 유지합니다. reconciled/stream_ready는 false로 유지합니다. 미해결 과거 요청 4건을 승인하거나 삭제하는 복구가 아닙니다.

## 실행

ZIP을 바탕화면에 풀고 기존 Docker를 유지한 상태에서 CMD를 여세요. 보안 설정 변경이나 다운로드한 CMD 실행은 필요 없습니다. 앱 이미지·소스·마이그레이션·의존성은 바꾸지 않습니다.

```cmd
cd /d "%USERPROFILE%\Desktop\windows-demo-tp-manual-close-fee-fix"
```

파일 해시를 검증한 뒤 적용합니다. 이 명령은 **장부 정정과 감사 이벤트/영수증 기록**을 수행하지만 거래소 POST/PUT/DELETE와 신규 주문은 수행하지 않습니다. 적용용 DB 리더 임대를 획득하므로 fence와 임대 감사 이력도 남습니다. 실패 시에도 임대 관련 이력이 생길 수 있으며 자동 재실행하지 않습니다.

아래 `RUN_COMMAND.txt`의 한 줄을 CMD에 붙여 넣으세요. `--apply`를 빼면 거래소 읽기 검토만 수행합니다.

성공 결과: `SIGNED_EXTERNAL_CLOSE_ADOPTED_ENTRIES_STILL_PAUSED`, CLOSED/open_quantity=0, paused=true, leader_released=true, order_writes=0. 결과 화면을 보내주세요. 차단되면 재실행/새 작업 ID/과거 복구 적용을 하지 말고 출력을 보존하세요. `application_may_have_completed`는 정정 쓰기 호출이 시작된 뒤 결과를 확정할 수 없을 때 true이며, 호출 전에는 false입니다. `lease_changes_possible`은 임대·감사 기록 가능성을 따로 나타냅니다. 불일치 시 값·응답 전체를 출력하지 않고 `mismatched_trade_fields`의 필드 이름만 표시합니다.

중복 적용은 영수증을 확인하고 `ALREADY_RECORDED_NO_ACTION`으로 종료하며 추가 장부 쓰기나 거래소 요청을 수행하지 않습니다. 이 경로는 거래소의 현재 상태를 재확인했다는 뜻이 아닙니다.

## 검사 범위와 남은 작업

읽기 전용 DEMO SDK와 GET-only 감사 클라이언트로 원본 진입·종료 주문, 해당 신호 이후 BTCUSDT 체결 코호트 정확히 2건, 원래 SL/TP의 CANCELED/EXPIRED, 두 운영 스냅샷 일치, 모든 종목의 포지션/활성 주문 없음, 레버리지2/격리, 기존 입출금과 손실 게이트를 확인합니다. 이 검토는 계좌 전체의 과거 모든 거래를 감사했다는 뜻이 아닙니다. 원래 전체 이력 복구 규칙을 완화하지 않습니다.

20초·서명 GET64·시각 조회3의 상한이 있으며 자동 재시도·응답 캐시·쓰기 전송은 없습니다. 실제 표준 클라이언트에서는 기존 HTTPS 연결 재사용 도구를 적용하고 반드시 닫아 원본 전송을 복원합니다. 수정된 데이터는 기존 DemoStore 임대·fencing·행 잠금·감사/outbox 트랜잭션으로 한 번에 기록합니다. 직전 원장 일치, 증거 신선도와 날짜/손실 한도를 쓰기 시점에도 확인합니다. 일치하지 않으면 정정 트랜잭션은 롤백합니다.

조회 제한 원인은 아직 수정하지 않았습니다. 당시 GET397건/약54.8초 및 RATE_LIMITED/PING, 자동 종료 요청0, UNKNOWN flat이 기록됐고 사용자가 수동 정리했습니다. HTTP 418/429 구분·서버 가중치·Retry-After는 기존 결과에 없어 정확한 한도 원인을 단정할 수 없습니다. 이 정정은 TP 검증 성공이나 새 주문 허용을 의미하지 않습니다. 조회량/가중치·쿨다운과 정리 절차를 검토하기 전 재시험하지 마세요. Phase 4 전체 완료·LIVE·다음 단계 승인은 변경하지 않습니다.
