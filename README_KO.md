# income 페이지를 반영한 예산 검사 후보 — 2026-11-07 (한국시간)

income을 1페이지로 보고 정한 진입·보호 1,500 / 종료 3,000 가정을 그대로 사용하면 새 후보는 **진입 준비 전에 거부**합니다. 최대 10페이지와 기존 flat 확인 최대 4회를 비용 검사에 반영했습니다. 실제 거래소·Windows·계좌 DB에는 적용하지 않았고 기존 CLI에서 자동으로 켜지지 않습니다.

## 최종 검증

단일 실행 **1,062개 테스트 통과**(단위 855개, 통합 207개, 233.04초). 전체 코드 Ruff, 134개 소스 mypy, 변경 파일 format/diff 검사, 기준 소스에 대한 누적 21개 파일 패치 적용·해시 검증도 통과했습니다.

10페이지·확인 4회 대조군에서 전체 이력 snapshot은 20회, 종료 주문은 1회였습니다. 해당 합성 cleanup 비용은 14,102로 계산된 여유 24,960 안에 있었습니다. 이 결과를 실제 거래소 비용 상한으로 해석하지 않습니다.

## 계산과 적용 위치

기존 감사에서 관찰한 기본 경로의 스냅샷 수(준비 3, 예약·초기 보호 6, 종료 12)와 1페이지 비용 가정(진입·보호 1,500, 종료 3,000)을 출발점으로 사용합니다. 이는 모든 분기의 비용 상한을 입증한 값이 아닙니다. 새로운 숫자는 다음 **보수적인 모델 가정**입니다.

income 1회 비용을 30, 준비 1페이지 비용을 712로 선언했을 때:

| 항목 | 계산 | 요구 가정 |
|---|---|---:|
| 준비 | 712 + 3 × (10−1) × 30 | 1,522 |
| 예약·초기 보호 | 1,500 + 6 × (10−1) × 30 | 3,120 |
| 종료 1회분 | 3,000 + 12 × (10−1) × 30 | 6,240 |
| 종료 확인 여유 | 4 × 6,240 | 24,960 |

종료 전체 경로 1회분을 4번 예약하므로 실제로 한 번만 실행하는 명령 비용까지 반복 계상하는 보수성이 있습니다. **청산 주문을 4번 보내거나 SDK 재시도를 추가하지 않습니다.** 기존 종료 명령 최대 1회와 확인 관찰 최대 4회는 그대로입니다.

이 계산을 기존 plan의 진입·보호/종료 여유와 비교합니다. 작은 가정을 유지하면 `INCOME_PAGINATION_ALLOWANCE_INSUFFICIENT`로 멈춥니다. 준비 직전과 예약 직전에 다시 검사하며, 준비 비용은 미리 차감하거나 중복 차감하지 않습니다. 원래 `precheck_preparation`, `admit_entry`, 전송별 차감·헤더 신선도·cooldown 검사도 수행합니다. income 경로 비용이 없으면 임의의 싼 값으로 대체하지 않습니다.

**이 가정들은 한도 6,000 안에 들어가지 않습니다.** 부족한 plan을 거부하는 것이 이번 변경의 결과이며, 진입을 가능하게 만들려고 공개 한도나 안전 증거를 바꾸지 않았습니다. 계산을 통과해도 실제 서버의 전역 IP 요청 여유를 예약하거나 거래를 승인한 것은 아닙니다.

## 기존 증거의 유지

snapshot 파서의 10페이지/페이지당 1,000건 제한은 숫자와 동작을 유지하고 이름 있는 상수로만 바꿨습니다. 10번째 페이지도 가득 차면 여전히 조회 미완료로 거부합니다. transfer/보너스 처리와 시간 범위·fingerprint는 바꾸지 않았습니다.

flat 확인 횟수 4는 실행 코드와 예산 코드가 같은 상수를 참조하게 했습니다. 기존 parser와 상수 치환 뒤 AST가 같은지 검사하고, 준비·예약·제출·보호·청산·flat 확인 함수의 본문도 대조합니다. 잠금 사양과 설치 승인 해시는 바꾸지 않았습니다.

## 격리 검증

- 기존 1,500/3,000 가정은 합성 한도 6,000과 100,000 모두에서 새 주문·예약 전에 거부합니다.
- 명시적으로 큰 예산을 준 **합성 한도 100,000 대조군**에서는 TP/TP 미체결/부분체결/미체결과 종료 직전 income 1·3·10페이지 증가를 검증합니다. 실제 한도를 100,000으로 바꾸거나 6,000에서 같은 주문이 가능하다고 주장하지 않습니다.
- 종료 확인의 원래 증거를 매번 조회하되 처음 3회 수용하지 않는 주입 시험에서 전체 이력 snapshot 20회와 종료 주문 최대 1회를 검사합니다. 마지막 확인까지 실제 포지션은 flat으로 유지합니다.
- 준비 뒤 plan을 작은 값으로 바꾸면 예약 직전 재검사에서 거부합니다.
- 10번째 페이지도 가득 찬 경우와 공유 IP 급증/429의 기존 거부·EMERGENCY/UNKNOWN·cooldown을 유지합니다.

합성 페이지 데이터는 비용 부하를 만들기 위한 COMMISSION 행이며 실제 수수료 회계 이력을 재현한 것이 아닙니다. 최종 테스트 수·시간은 `VALIDATION.json`, JUnit은 `test-results/`, 요청 추적은 `synthetic_reports/`에 있습니다. 테스트 통과에는 의도한 거부와 잔존 노출 보고도 포함됩니다.
