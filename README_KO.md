예산이 부족한데도 계좌 재확인과 가격 계획 조회를 진행한 뒤 뒤늦게 멈추는 비용을 줄이는 후보입니다. **거부 시점을 앞당길 뿐, 주문 승인 조건을 완화하지 않습니다.** 실제 Windows·거래소·계좌 DB에는 적용하지 않았고 기존 CLI에서 자동 활성화되지 않습니다.

## 검증 결과

단일 실행에서 **992개 테스트 통과**(단위 820개, 통합 172개, 154.87초). 전체 코드 Ruff와 133개 소스 mypy도 통과했습니다.

## 변경

새 `PrecheckedBudgetedTPTriggerCoordinator`는 새 작업의 `resume_entries`와 `prepare` 호출 전에 예산을 검사합니다. `현재 보수적 사용량 + 준비 비용 가정 + 기존 진입·보호 비용 가정 + 기존 종료 비용 가정 + 여유분`이 공개 한도 안에 들어야 준비를 계속합니다. 예산 헤더는 기존과 같이 5초 이내여야 합니다.

이 검사는 주문 허가·신호·예약을 만들지 않으며 예측 비용을 미리 차감하지도 않습니다. 통과한 뒤 실제 요청은 원래대로 차감하고, 예약 직전의 `admit_entry`와 전송 직전 검사를 다시 수행합니다. 준비 중 공유 IP 사용량이 늘거나 준비 비용을 낮게 가정해도 뒤의 검사가 유지됩니다. 분 경계나 낮아진 헤더로 예산을 복구하지 않습니다.

새 작업에만 선택 hook을 적용합니다. 기존 작업 ID 복구 분기와 원래 coordinator·CLI는 그대로입니다. 앞선 계정 알림 묶음 후보를 상속하되 부분체결·미체결·긴급 알림의 기존 처리 조건도 유지합니다.

## 초기 비용 모델

이번 합성 준비 가정은 다음 비용을 포함합니다.

- `resume_entries`의 운영 계좌 스냅샷 1회와 preview의 시작·종료 스냅샷 2회.
- 예약 시점 검사까지 시계 GET 3회.
- 공개 거래 조건 메타데이터 1회, book/mark/kline 조회 각 1회.

실측 프로파일의 인접 응답 차이를 참고한 합성 비용으로, 운영 스냅샷은 dual-side 가정 30에서 191, 35에서 196입니다. 따라서 준비 비용 입력은 각각 **697, 712**입니다. 엔드포인트 비용의 확정값이나 상한이 아니며, 미측정 공개 경로 비용 40도 입증된 최대값이 아닙니다. 추가 income 페이지·공유 IP 활동·예상하지 못한 추가 요청을 완전히 예측하지 못합니다. 이것이 뒤의 실제 사용량 검사와 예약 검사를 유지하는 이유입니다.

분당 한도 6,000, 과거 주문 19개, 진입·보호 1,500/종료 3,000/여유 300이라는 기존 가정에서는 초기 준비 전에 거부합니다. 공개 호가·mark·kline을 조회하지 않고 신규 주문·예약도 만들지 않습니다. 차단 뒤에는 기존 전체 이력 flat 확인 5회를 그대로 수행합니다. 최종 보고는 TP 검증 성공으로 올리지 않습니다.

**여전히 실제 6,000 모델에서 신규 진입을 승인하지 않습니다.** 이미 예산 부족인 준비의 낭비를 줄이는 변경이지, 신규 DEMO 주문이나 운영 재개를 가능하게 하는 변경은 아닙니다.
