# TP 분별 예산 검토 — 읽기 전용

소스 `022b1ab001b58c1d84617a2071433c3ce8041764`
시험한 실행 후보 `fc986129bc99663533a2ea3be8335932454e78c7`

기존 실행 소스는 바꾸지 않았습니다. 새 파일은 오프라인 분석기와 시험 코드 4개뿐입니다. 실제 DEMO/LIVE API·주문·Windows DB에 접근하지 않았으며 설치나 거래 활성화 명령은 없습니다. 기존 6,000 진입 차단과 기본 실행 거부를 유지했습니다.

## 핵심 결과

누적 비용은 1분 한도와 직접 비교할 수 없습니다. 실제 경과 시간 300초를 유지한 가짜 거래소 시험을 실행하고, 관찰된 고정 분 및 실행 시작 시각을 달리한 모든 분 경계의 최대 비용을 계산했습니다.

| 합성 시나리오 | 전체 누적 비용 | 관찰된 고정 분 최대 | 시작 시각 변경 시 1분 최대 | 최종 flat 판정 |
| --- | ---: | ---: | ---: | --- |
| 정상 TP 체결, 300초 | 15,150 | 4,653 | 5,433 | VERIFIED_FLAT |
| 취소 반영 지연, 300초 | 16,160 | 5,539 | **6,778** | VERIFIED_FLAT |
| 취소 실패, 300초 | 22,801 | **12,180** | **13,419** | UNKNOWN |
| 4Hz 이벤트·50ms 응답 지연, 관찰 20초 요청 | 11,616 | **11,616** | **11,616** | VERIFIED_FLAT |
| 같은 지연·관찰 45초 요청, 수집 한도 도달 | 12,442 | **12,292** | **12,430** | UNKNOWN |

정상 TP 경로가 이번 측정에서 6,000 아래였어도, **취소 지연·실패 경로는 한도를 초과**합니다. 이전의 청산 구간 5,126만으로 진입을 허용하면 안 됩니다. 취소 지연은 원래 시작 시각에서는 고정 분 최대가 5,539지만, 같은 요청열을 다른 시각에 시작하면 6,778이 한 분에 모일 수 있습니다. witness_offset_ms와 해당 구간의 요청 번호를 JSON에서 확인할 수 있습니다.

앞의 300초 3건은 실제 단조시계 기준 약 300.642초, 303.778초, 303.977초가 걸렸습니다. 관찰 300초 상수와 원래 보호·청산·이력 검증은 유지했습니다. 가짜 거래소 시각은 기존 fixture의 UTC 기준에서 실제 단조시계와 1:1로 진행했으며 시간 가속을 하지 않았습니다.

50ms 지연의 관찰 45초 요청 사례는 기존 Capture 도우미의 128개 힌트 제한에 도달했습니다. 제한을 늘리지 않았습니다. 하위 최종 확인이 VERIFIED_FLAT이어도 세션 수집 오류가 있었으므로 전체 보고서는 UNKNOWN을 유지합니다. 제한에 도달하지 않는 별도 20초 요청 사례도 검증했습니다.

## 오프라인 분석기

review_tp_minute_budget.py는 표준 라이브러리만 사용하며 JSON 파일만 읽습니다. HTTP, DB, 자격증명 조회, 주문 기능은 없습니다. 로컬 Python에서 다음처럼 원본 기록을 재계산할 수 있습니다.

```text
python review_tp_minute_budget.py raw_reports/quiet_delayed_cancel.json --limit 6000 --reserve 300
```

분석기는 다음을 구분합니다.

- 전체 누적 모델 비용과 원래 기록의 고정 분별 비용
- 임의의 실행 시작 시각에서 같은 분에 들어갈 수 있는 60초 요청 비용과 구체적인 분 경계 witness
- ms 내림 기록의 경계 오차를 보수적으로 포함한 60,001ms 구간. --timing-uncertainty-ms로 추가 오차를 명시할 수 있습니다.
- 관찰된 카운터의 불일치·미확정 응답·공유 IP에 해당할 수 있는 추가 카운터. 낮은 카운터로 요청 비용을 환불하지 않습니다.

미등록 경로, 비용 모델 불일치, 잘못된 숫자·순서·시각은 거부하고 원본 query/body/key를 출력하지 않습니다. 선형 시간 계산을 독립적인 분 경계별 완전탐색 모델과 비교 검증했습니다.

결과가 MEASURED_REQUESTS_FIT_ASSUMPTIONS_ONLY이어도 실행 승인으로 바꾸지 않습니다. 모든 결과의 actual_execution_approved와 runtime_admission_changed는 false입니다. source query 범위를 이 분석기가 검증했다는 주장도 하지 않습니다.

## 검증과 제한

**88개 통과**: 자연시간 300초 3건, 추가 지연/수집 한도 2건, 분석기 단위 46개, 기존 예산 단위 30개, 완료 증거 계약 5개, 기존 진입 차단 2개입니다. Ruff와 mypy(138개 운영 소스 파일)도 통과했습니다. 검사 XML은 test-results/에 있습니다.

실제 PostgreSQL의 분리 스키마와 로컬 WSS를 사용하며 HTTP·주문·체결은 모두 가짜입니다. 요청열은 분리 fixture 초기화 이후 run_admission_candidate 호출 구간을 기록했으며, fixture 준비·외부 작업·다른 IP 사용량은 포함하지 않습니다. 실행 모델 한도는 100,000이고, 재검토 한도는 6,000입니다. GET 비용은 기존 명시 모델, 변경 요청별 비용은 40을 가정했습니다. 6,000으로 신규 진입을 실행한 시험이 아닙니다. 엔드포인트 비용 상한, 별도 주문 횟수 제한, 실제 공유 IP 용량, 실제 거래소의 카운터·분 경계는 증명하지 않았습니다.

quiet_tp 하나가 여유분 300까지 포함해 측정 범위에 들어맞는다는 것은 그 요청열의 결과입니다. 실패 비용이나 다른 이벤트 빈도까지 보장하는 상한으로 사용할 수 없습니다. 기존 진입 가드는 낮추지 않았고 분 경계에서 크레딧을 새로 제공하는 실행 코드도 추가하지 않았습니다.

## 파일과 다음 작업

raw_reports/는 가짜 요청 경로·모델 비용·상태 기록 5개, minute_reviews/는 분석기 출력 5개입니다. MINUTE_SUMMARY.csv로 비교할 수 있습니다. source/와 source.patch는 직전 후보 대비 새 파일 4개이며 기존 실행 코드 전체는 source hash로 동일함을 확인했습니다. 분석기는 최상위에도 복사해 두었습니다. manifest는 자기 자신을 제외한 파일 SHA256 목록입니다.
