# 운영 스냅샷의 검증된 수동 청산 이력 생략 후보

**과거 수동 청산 기록 한 건의 조회3건만 생략하는 후보를 합성 활성 TP 흐름까지 검증했습니다. 운영에는 적용하지 않았습니다.** 현재 설치된 읽기 전용 준비 상태 확인의22회 경로는 유지됩니다. 이 패키지는 검토용이며 Windows 실행·설치 명령이 없습니다.

## 이번 범위

기존 운영 스냅샷은 앱 청산이 완료된 CLOSED 기록이 두 새 열린 주문 목록에 없으면 과거 ID 조회를 생략합니다. 이 후보는 이미 채택된 수동 청산 영수증에 같은 조건을 적용합니다. 대상은 이전에 검토한 사건041d1f35-870e-46cb-aad2-ed6059bc1095 한 건입니다.

단순 CLOSED 표시만으로 생략하지 않습니다. 수량/체결0.0007, 노출·잔량·위험0, 보호false, 원본 신호·진입/SL/TP ID·실패 이력·정확한 순손익−0.07032487·두 체결ID·원래 주문 필드·영수증 출처와 시각/해시 형식이 맞아야 합니다. 두 개의 **새** 열린 주문 목록에 원래 진입/SL/TP/청산 ID가 다시 나타나면 생략하지 않습니다.

현재 열린 주문, 부분체결, 미체결 잔량, 미확인 상태와 다른 과거 기록은 기존 조회를 유지합니다. 계정 설정·전역 포지션·일반/알고 주문·잔액·증거금·income은 기존대로 새로 조회합니다. REST 응답을 캐시하거나 income 범위를 줄이지 않습니다. 위험 락을 해제하거나 요청 이력을 정리하지 않습니다.

## 영수증 시각과 현재 평가 시각

앞선 준비 상태 확인은 수동 청산 채택 당시의 금융 스냅샷 시각까지 묶었습니다. 활성 운용에서는 계좌 value.as_of가 정상 대조 때마다 갱신됩니다. 과거 종료의 불변 증거를 그 새 평가 시각과 비교하면 매번 최적화가 풀리므로, 이 후보에서는 **현재 평가 시각과 과거 종료 영수증의 시각을 분리**했습니다.

그 외 영수증의 원본 주문/신호/ID/금액/체결/실패 이력 검사는 그대로입니다. 종료 기록 자체가 변하면 기존 조회로 돌아갑니다. 미래 영수증 시각은 수용하지 않습니다. 현재 계좌 데이터와 freshness/진입 게이트는 기존 코드로 검증하며, 과거 영수증으로 현재 포지션이나 금융 상태를 추정하지 않습니다.

## 중요한 통합 조건

처음에 coordinator 쪽만 후보로 바꾸자 진입 전 미리보기와 상태 fingerprint가 달라져 **기존 게이트가 신규 진입 전에 차단**했습니다. 이 결과를 성공으로 바꾸거나 fingerprint 비교를 우회하지 않았습니다.

후보 흐름의 검증에서는 coordinator와 진입 전 preview의 operational reader를 모두 같은 후보로 연결했습니다. 반면 전체 이력 기반 flat 확인은 기존 reader를 그대로 사용했습니다. 두 방식을 섞으면 진입0건으로 차단되는 별도 음성 사례도 포함합니다.

이 연결은 격리 테스트의 monkeypatch 안에서만 수행했습니다. 설치된 모듈이나 CLI에는 후보 import/flag/hook을 추가하지 않았습니다. source.patch는 승인된70a854c의 parser에 대한 재현용 단일 파일 패치이며, 현재 설치 가드의 승인 해시를 바꾸지 않았습니다. 운영 컨테이너에 이 패치를 적용하지 마세요.

## 검증 결과

단일 실행 **793개 통과**: 승인된 기준 코드의753개 회귀 + 후보40개(스냅샷/반례24, 수명주기16). 전체 Ruff와133개 소스의 mypy도 통과했습니다. candidate_snapshot.py를 전체 운영 모듈로 교체한 뒤 모든 호출처/설치 가드를 통합 검증한 결과는 아닙니다. 기준 운영 소스는 변경하지 않았습니다.

| 검사 | 결과 |
|---|---|
| 종료가 입증된 과거 ID 조회 | 대상 운영 스냅샷마다3회→0회 |
| 현재 보호 포지션·부분체결·미보호·EXIT_PENDING | 현재 주문/보호 조회와 금융 필드 유지 |
| 원래 ID가 열린 주문 목록에 재등장 | 원본과 동일하게 조회 |
| 불완전/변조 영수증·실패 이력 | 원본 조회 유지 |
| 합성 TP 체결 | 기존 signed TP 증거→원래SL 정리 순서 유지 |
| TP 미체결·미체결 진입·부분체결·수량 증거 불일치·취소 확인 불가 | TP 성공으로 수용하지 않음 |
| 정상적으로 flat 확인을 완료한 흐름 | 기존 전체 이력 snapshot5회, 과거 원래 ID조회15회 유지 |
| 대조/미리보기의 reader 혼용 | 진입0건으로 차단 |
| 비JSON429 주입 | 첫429 이후 재전송 없음, cooldown 유지, EMERGENCY/UNKNOWN 및 잔존 노출 보고 |
| 장부 이력·기준·고점 | 기존 수동 청산 기록과 영수증 및 기준 보존 |

수명주기는 격리 PostgreSQL·localhost WebSocket·합성 SDK 응답으로만 실행했습니다. 실제 거래소 주문이나 사용자 DB 변경은0건입니다. TP 성공 표시는 합성 결과이며 실제 부분체결 보호/TP 승인의 추가 증거가 아닙니다.

## 절감의 의미와 남은 한계

확인한 효과는 **동일한 적격 스냅샷 입력에서 과거 조회3건 감소**입니다. 전체 수명주기의 스냅샷 횟수는 WebSocket 스케줄링에 따라 달라졌으므로 원본/후보 총 요청 수를 그대로 성능 향상률로 계산하지 않습니다.

이3개 경로의 비용을 각각1로 가정해도 고비용 전역 조회는 그대로 남습니다. 이전의28→22회 같은 GET 건수 비율을 IP weight 절감률로 바꾸지 않습니다. synthetic_reports의 hypothetical_old_id_weight1_saving도 실제 가중치 실측이나 보장된 상한이 아닙니다.

이번 합성 실행에는 실제 분당6000 한도를 통과했다는 의미가 없습니다. 실제 비용/동시IP 활동·income 페이지·종료 여유를 새로 보장하지 못했습니다. 이전 예산 후보가6000 모델에서 신규 진입 전에 거부한다는 사실도 바꾸지 않았습니다. 따라서 후보 검증만으로 실제 TP 시험을 재개하지 않습니다.

## 출처와 재현

- 기준:70a854ca677b0a8e3355b7f99ac0e0cce3bc6ba5(설치 완료된 준비 상태 확인 최적화)
- candidate_snapshot.py: 독립적인 미설치 parser 후보
- source.patch: 위 기준 parser에 적용 가능한 재현용 패치(격리된 개발 체크아웃 전용)
- STRUCTURE_PROOF.json: 기존 parser에서 조건 하나를 제거하면 AST가 동일함을 확인; 숫자/필드/계좌/income 파싱과 전체 이력 함수 본문 유지
- SUMMARY.json, synthetic_reports/:16개 합성 수명주기 결과
- VALIDATION.json, test-results/: 테스트 범위와 JUnit

개발자는 승인된 기준 소스와 기존 의존성·폐기 가능한 PostgreSQL에서 이 디렉터리의 두 test 파일을 pytest로 실행할 수 있습니다. verify_structure.py는 기준 소스를 cwd로 하여 실행합니다. API 키는 필요하지 않습니다. 사용자 Windows에는 이번 단계에서 실행할 명령이 없습니다.
