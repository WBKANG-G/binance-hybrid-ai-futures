# 보호된 포지션의 계정 알림 묶음 처리 후보 — 2026-11-06 (한국시간)

SL·TP 검증이 끝난 포지션에서 `ACCOUNT_UPDATE` 알림만 최대 250ms 동안 모아 한 번의 기존 REST 대조로 처리하는 후보입니다. 반복 조회를 줄이되 flat 확인용 전체 이력 조회 5회와 기존 보호·청산 증거는 그대로 유지합니다. 실제 거래소·Windows·계좌 DB에는 적용하지 않았고, 기존 CLI에서 자동 활성화되지 않습니다.

## 검증 결과

단일 실행에서 **961개 테스트 통과**(단위 801개, 통합 160개, 150.33초). 전체 코드 Ruff와 133개 소스 mypy도 통과했습니다.

대표적인 보호 포지션/TP 미체결 알림 집중 모델에서 HTTP 요청은 **1,672 → 1,062회(36.48% 감소)**, 가정 가중치 합계는 **17,653 → 9,945(43.66% 감소)**였습니다. 둘 다 여러 분 운용을 재현하지 않은 압축 모델의 총량입니다. flat 확인용 전체 이력 조회는 양쪽 모두 5회였고, 실제 부분체결·TP 승인 증거를 새로 얻은 것은 아닙니다.

## 적용 조건과 차단 동작

- ISOLATED BTCUSDT, DEMO 검증용 LONG, 최대 0.0007 BTC/100 USDT의 완전 체결 포지션 1개만 대상입니다. SL·TP ID, 검증 증거, 보호 상태, 로컬·거래소 포지션 수량, 신선한 stream/reconciliation 시각이 모두 일치해야 합니다.
- 미체결 잔량, 부분체결, 종료 의도, 알 수 없는 주문 상태, 검증되지 않은 보호, 오래된 계좌 상태, 위험 잠금, 예산 중단에는 추가 묶음 대기를 적용하지 않습니다.
- 대기 전에 `stream_ready`와 `reconciled`를 무효화합니다. 테스트에서 이 상태의 실제 진입 게이트 `_fresh`가 거부됨을 검사합니다. 다음 event 처리는 원래 시계 검증·전체 snapshot pair·보호 재확인을 실행합니다.
- `ORDER_TRADE_UPDATE`, `ALGO_UPDATE`, `MARGIN_CALL`, `ACCOUNT_CONFIG_UPDATE`, `TRADE_LITE` 등 나머지 유효 알림은 추가 묶음 대기 없이 처리합니다. 계정 알림 뒤에 이런 알림이 도착하면 대기를 끝냅니다. 그 뒤 더 최신 계정 알림이 와도 긴급 해제 표시는 유지됩니다. 각 프레임의 원래 시간·유효성 검사는 생략하지 않습니다.
- 잘못된 JSON·종류·시각, listen-key 만료, 큐 초과, 시계 검증 취소는 실패로 남습니다. 알림 묶음으로 숨기지 않습니다. 원래 이벤트 시각을 고쳐 쓰지 않습니다.
- 대기 마감은 wakeup 시점에 고정합니다. 계속 도착하는 알림 때문에 마감이 연장되지 않습니다. 추가 대기는 최대 250ms이며 DB/REST/WSS 지연까지 250ms로 보장한다는 뜻은 아닙니다. 기존 시계 검증 지연도 우회하지 않습니다.
- private 세션 취소 때 DB 작업을 회수하는 원래 `settled_call`을 사용합니다. 실제 429 cooldown, 종료 요청 ID, fencing, reduce-only 종료, 원래 SL 삭제 전 TP 증거를 유지합니다.

`CoalescedBudgetedTPTriggerCoordinator`를 별도로 구성한 격리 테스트에서만 이 경로를 사용했습니다. 기존 coordinator와 CLI에는 hook이 없어 원래 take 경로를 사용합니다. 잠금 사양과 설치 승인 해시는 바꾸지 않았습니다.

## 비용 비교의 의미

`COMPARISON.json`은 합성 REST·시계·주문과 실제 격리 PostgreSQL·로컬 WebSocket으로 얻은 요청 수 비교입니다. 이벤트 집중 관찰을 2초로 압축한 모델이며 거래소 실측 성능이나 분당 사용량의 증거가 아닙니다. 단위 비용은 사용자 프로파일의 인접 응답 차이에서 가져온 가정이며, 공유 IP 활동을 포함할 수 있습니다. 미측정 경로 비용 40은 입증된 상한이 아닙니다.

반복 조회 감소 효과를 비교하는 대조군은 합성 한도 100,000으로 제한을 제거했습니다. **실제 한도를 100,000으로 설정하지 않았습니다.** 부분체결·미체결의 요청 수 차이가 있어도 묶음이 적용된 것은 아닙니다. 해당 사례의 묶음 적용 횟수는 반드시 0이며, 벽시계 스케줄링과 이벤트 수 차이가 요청 수에 영향을 줍니다.

실제 공개 한도를 반영한 **6,000 모델은 이전 예산 검사대로 신규 진입 전에 차단**됩니다. 이 개선은 활성 관찰의 반복 비용을 줄이는 후보이며 초기 진입·보호·종료 예산 문제를 모두 해결하지 않습니다. 공유 IP 급증 모델에서는 여전히 자동 종료가 막히고 EMERGENCY/UNKNOWN을 남깁니다. 운용 재개나 신규 실제 DEMO 주문의 승인 증거가 아닙니다. 일시정지를 유지하는 단계입니다.

## 검증과 재현

최종 실행 수·시간과 정적 검사는 `VALIDATION.json`, JUnit은 `test-results/`, 원시 합성 요청 추적은 `synthetic_reports/`에 있습니다. 새 테스트는 대기 전 진입 무효화, 비대상 상태의 무대기, 긴급/실패 해제, 고정 마감, 취소/overflow와 기존 이력·기준값 보존을 검사합니다. 정상 종료 사례는 **전체 이력 flat snapshot이 정확히 5회** 호출됐는지도 확인합니다.

`source.patch`는 배포 기준 `e9327bd4729c7b5a4eeebff0e309f0f631395098`에 적용하는 **누적 검토 패치**입니다. 앞선 요청 예산 후보의 변경도 포함합니다. 앞선 후보 자체는 `c24fb4e2412ecd1d123bde407a314301954a54a9` 보고서와 연결됩니다. `source/`와 `SOURCE_REFERENCE.json`으로 변경 파일을 대조할 수 있습니다.

재현은 기준 소스를 별도 클라우드 체크아웃하고 폐기 가능한 PostgreSQL만 연결해 수행해야 합니다. 사용자 Windows 컨테이너나 실제 DB에서 패치를 적용하거나 테스트를 실행하지 마십시오. 이 패키지는 설치 명령이나 실행 승인을 요청하지 않습니다. 기존 설치가드는 미승인 후보를 DB 조회 전에 거부하도록 유지했습니다.
