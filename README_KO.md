## 확인된 실행 순서

1. demo_validation.prepare: 생성 시점부터10초 신호 유효기간. validate_once는 on_ready 콜백이 반환된 뒤300초 관찰을 시작한다.
2. demo_stream.session: 콜백 완료를 기다린 뒤 lease 갱신/시계 동기화, EventInbox.take를 수행한다.
3. 이벤트가 오면 coordinator.event → connected → REST reconcile이 끝난 뒤 expire를 호출한다.
4. 무소식이면 take 기본5초 대기 → ping/pong(최대5초) → connected/REST reconcile이 끝난 뒤 expire를 호출한다.
5. expire가 잔여 수량과 저장된 만료를 확인해 cancel을 호출한다. 취소 의도와 실제 DELETE는 별개 단계이며 이후 다시 reconcile한다. settled_call은 진행 중인 작업을 끝까지 기다려 중복 DB 작업을 피한다.

따라서10초는 신호 유효기간이며, 거래소 주문을 그 시각에 반드시 취소하는 독립 타이머가 아니다. 콜백/수신 대기/pong/직렬 REST 작업/DB 잠금이 만료 검사 이전에 올 수 있다. 여러 REST 호출이 직렬이므로 지연 전체가 단일5초 제한 안에 끝난다고 주장할 수 없다.

## 검증

제품 코드는 수정하지 않았다. 실제 session 함수를 실행하고 합성 시계/소켓/저장소/코디네이터를 주입한3개 테스트로 무소식 대기 후 재조회, 이벤트 후 재조회, 느린 준비 콜백이 만료 검사를 뒤로 미루는 순서를 확인했다. 합성 사례는 실제 발생의 추정 분해가 아니다. 거래소/DB/실제 주문 호출은 없었다. 기존 EventInbox 단위 시험도 함께 실행해 총13개가 0.31초에 통과했다. Ruff 검사/포맷 검사도 통과했다.

## 한계와 정정

실제7.070초의 단계별 소요 시간은 기존 자료에 없다. 5초 대기+2초 REST였다고 확정하지 않으며 다른 지연 기여도도 배제하지 않는다. 감사 이벤트 as_of는 정확히는 DB 행 잠금 획득 후 apply 직전에 캡처한 시각이다. 이전 진단의 LOCAL_TRANSACTION_START 문구는 너무 넓은 표현이었다. 거래소 송신/응답/커밋 시각은 아니다. 원격 updateTime도 최신 상태 갱신 시각이며 네트워크 취소 송신 시각은 아니다.

## 후속 구현 방향

유효기간10초와 주문·수량·보호 정책을 유지하면서, 준비 콜백 직후 및 이벤트 대기 전에 만료를 확인하고 대기 시간을 가장 가까운 만료에 맞춰 제한하는 변경을 별도 검토할 수 있다. 진행 중인 REST/DB 작업의 안전한 종료, 리스/펜스와 취소/부분체결 재조회는 유지해야 한다. 이 문서는 해당 변경이나 엄격한 취소시한 보장을 구현하지 않았다. 새 실제 주문 재시도 없이 진행한다. Phase4 전체 완료/LIVE/Phase5와 구분한다.
