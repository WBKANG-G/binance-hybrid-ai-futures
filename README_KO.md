# 불명확한 보호 주문 취소를 관찰하는 후보 — 검토 전용

후보 `80f6edcbc8aafe3f1c8a2090c53f94f5a5194597`
직전 검토 소스 `022b1ab001b58c1d84617a2071433c3ce8041764`
현재 Windows 설치 기준 `4e967dc6751c6f04786ba63cdcc97e7eb1c80a39`

이 패키지는 설치용이 아닙니다. 실제 DEMO/LIVE API·주문·Windows DB에 접근하지 않았습니다. 기존 6,000 진입 차단과 기본 실행 거부를 유지하며 새 거래 활성화 CLI는 없습니다.

## 결과

관찰 시간을 줄이지 않은 300초 가상 거래소 시험 4개를 실행했습니다. 이전과 동일한 모델 비용 및 분 경계 분석기로 계산했습니다.

| 시나리오 | 관찰된 고정 분 최대 | 시작 시각에 따른 1분 최대 | 최종 flat 판정 |
| --- | ---: | ---: | --- |
| 정상 TP | 4,657 | 5,433 | VERIFIED_FLAT |
| 취소 ACK 반영 지연 | 5,539 | **6,778** | VERIFIED_FLAT |
| 취소 실패 지속 | 4,013 | **5,187** | UNKNOWN |
| 취소 오류 이후 나중에 취소 확인 | 5,879 | **7,118** | VERIFIED_FLAT |

지속 실패 경로의 1분 최대 모델 비용은 **13,419에서 5,187로 감소**했습니다. 취소 요청은 한 번만 실행되고 나머지 관찰은 GET만 사용했습니다. 하지만 UNKNOWN을 유지하므로 청산 완료가 아닙니다. 취소 오류 뒤 실제 취소가 확인되는 경로는 원래 전체 증명을 수행하며 7,118이 필요했습니다. **지연·복구 경로가 여전히 6,000을 초과**하므로 신규 진입을 허용할 근거가 아닙니다.

짧은 대조 시험에서는 지속 실패 청산 구간 비용 3,416, 오류 뒤 취소가 확인되는 구간 5,466을 측정했습니다. 누적 비용과 분별 한도는 구분해야 합니다. 모든 수치는 기록된 합성 요청열이며 모든 실패 조건의 상한은 아닙니다.

## 변경 동작

원래 전체 QUERY 쌍 스냅샷과 원래 fenced 보호 주문 정리를 먼저 수행합니다. 그 과정에서 취소 요청이 SDK 오류로 끝나면, 이전 전체 증명과 비교해 계정 상태의 변화가 대조 무효화뿐인지 검사합니다. SDK 실패 횟수는 서버에 DELETE가 전송되었거나 취소가 수락됐다는 증거로 쓰지 않습니다.

허용된 조건에서만 다음을 묶은 유효시간 8초의 관찰 권한을 만듭니다.

- 계정 상태 전체 해시와 현재 lease 소유자/fence
- 동일한 검증 작업 및 실패한 기존 보호 주문 ID
- 직전 대조 시각과 단조시계 경과 시간
- DB의 결정적 UUID5 미해결 표식 CANCEL_UNCERTAIN_REVIEW

관찰 권한이 유효한 동안에는 새 mode·전 종목 포지션·전역 일반/Algo 미체결 주문·기존 보호 주문 ID를 조회합니다. 모든 포지션이 0이고 일반 미체결 주문이 없으며, 알려진 실패/ACK ID만 아직 NEW인 경우에만 UNKNOWN으로 기다립니다. 이 경로는 POST/DELETE를 보내지 않고, financial 값이나 reconciled를 성공 상태로 바꾸지 않습니다. 작업 권한 확인 아래 일시정지도 유지합니다.

상태·작업 권한·시계·주문 범위가 달라지거나 시간이 지나면 관찰 권한을 버리고 원래 전체 검증으로 돌아갑니다. 그 원래 검증에서 새로 안전 조건을 확인하면 취소 정리를 다시 시도할 수 있습니다. 따라서 모든 조건에서 취소 재시도가 없다는 뜻은 아닙니다. 기존 총 4회 시도 및 1초 간격은 늘리지 않았습니다.

실패했던 취소가 해소되면 원래 전체 confirm_flat을 처음부터 수행해야 합니다. 실제 전체 성공 증명이 끝나고 로컬 상태도 유지된 경우에만 표식을 FULL_CONFIRMATION_COMPLETED로 전환합니다. 실패가 지속되면 미해결 표식, 일시정지, UNKNOWN을 남기며 보호 주문이 NEW로 남을 수 있습니다. 이 표식은 거래 재개 승인이 아닙니다.

## 안전 검증

**100개 통과**: 자연시간 300초 4건, 짧은 미확정/해결 흐름 2개, ticket·오류·공유 예산 20개, 진입 예산 통합 14개, 기존 첫 확인 오류 경로 18개, 잠금/무효 권한 계약 10개, 기존 확인 context 2개, 기존 예산 단위 30개입니다. Ruff와 mypy(139개 운영 소스 파일)도 통과했습니다.

만료·미래/NaN 시계·계정 상태 해시 변경·일시정지 변경·다른 종목 포지션·새 일반/Algo 주문·계정 모드 변경·잘못된 보호 메타데이터·HTTP500/429·공유 조회/시간/clock 예산 소진·fence 거절·마지막 전체 검증의 income 불완전·대기 중 잔고 변경을 확인했습니다. 대기 관찰의 손실 잠금 및 재무 값 보존도 검사했습니다. 첫 관찰은 진행 중인 전체 확인과 같은 자원 예산을 공유합니다.

이전 후보의 FirstConfirmation 클래스는 기존 lock 안의 같은 AST 본문을 확장용 메서드로 옮겼습니다. 원래 스냅샷 파서, _flatten, 최종 전체 확인 함수, 진입 예산은 변경하지 않았습니다. 새 클래스에서 실패 취소 처리 정책만 명시적으로 바꿨습니다.

## 범위와 한계

HTTP·주문·체결은 모두 가짜이고 PostgreSQL 분리 스키마와 로컬 WSS를 사용했습니다. 가상 한도는 100,000이며 분석 한도는 6,000입니다. GET 비용은 기존 모델, 변경 요청 비용은 각 40을 가정했습니다. 시간 가속을 하지 않았습니다. 요청 기록은 fixture 초기화 이후 후보 호출 구간이며 다른 프로세스·IP의 작업은 포함하지 않습니다.

관찰 권한이 무효화되는 조건은 더 비싼 기존 전체 검증으로 돌아가므로 이번 5,187을 최대 비용으로 사용할 수 없습니다. 실제 거래소 비용 상한, 별도 주문 횟수 제한, 공유 IP 용량, 모든 분별 실패 비용은 증명하지 않았습니다. 기존 청산 비용 가정이나 진입 가드를 낮추지 않았습니다.

## 파일

source/와 source.patch는 설치 기준 대비 누적 변경 파일 40개입니다. uncertain-only.patch는 직전 검토 소스 대비 10개 파일입니다. 실제 실행·시험에는 기준 저장소와 의존성이 필요합니다. natural_reports/는 300초 4건, minute_reviews/는 읽기 전용 분석 결과, 나머지 폴더는 짧은 안전 시험 기록입니다. query·키·서명은 기록하지 않습니다. MINUTE_SUMMARY.csv와 test-results/에서 수치와 검증을 확인할 수 있습니다. manifest는 자기 자신을 제외한 파일 SHA256 목록입니다.

최상위 review_tp_minute_budget.py로 기록을 오프라인에서 다시 계산할 수 있습니다. HTTP/DB/주문 기능은 없습니다.

```text
python review_tp_minute_budget.py natural_reports/quiet_failed_cancel.json --limit 6000 --reserve 300
```

다음 개발 대상은 취소 지연과 오류 뒤 복구 경로의 전체 성공 검증 비용입니다. Windows 설치나 거래 재개는 진행하지 않습니다.
