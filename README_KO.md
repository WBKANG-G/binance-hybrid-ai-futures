# DEMO 공유 요청 저장소의 독립 체크포인트 — 개발 검토 자료

직전 구현에 남아 있던 ‘유효한 과거 SQLite 백업 복원’ 탐지 공백을 보완했습니다.
공유 요청 파일 전체 상태의 해시를 독립 PostgreSQL 변경 이력과 대조하며, 실행 조립 경로가 이 기준을 필수로 요구합니다.

- 파일 하나만 과거로 되돌리거나 PostgreSQL 기준만 되돌리면 추가 사용을 차단합니다.
- SQLite 커밋 뒤 PostgreSQL 커밋이 실패해도 전송 토큰을 반환하지 않습니다. 불일치를 자동 수리하거나 예약을 반환하지 않습니다.
- PostgreSQL 기준 이력과 바인딩은 DB 트리거로 UPDATE/DELETE를 거부합니다.
- 실제 자식 프로세스를 두 저장소의 커밋 사이에서 SIGKILL한 경우에도 5,700 예약이 남고 재시작이 차단됐습니다.
- 별도 연결 풀을 사용해 계정 효과 트랜잭션 롤백이 공유 예약을 취소하지 못하게 했습니다.
- 읽기 전용 검사는 이력을 추가하거나 파일을 초기화·정리하지 않습니다.

테스트 1,165개, mypy 153개 소스, Ruff 통과.
실제 PostgreSQL과 SQLite로 백업 복원·커밋 실패·강제 종료·동시 8프로세스를 검증했습니다.
체크포인트를 필수로 쓰는 조립 경로에서도 모의 TP 청산과 부분 체결 후 위험 축소 청산을 전체 상태 확인까지 완료했습니다.
시작 대기는 가속했고 관찰은 0.8초이며 요청 가중치 시계는 실제 시간을 사용했습니다. 새 300초 자연 관찰이나 거래소 검증은 아닙니다.
Docker 스모크는 네트워크 없이 기본 차단과 해시 불일치 판정을 확인합니다. PostgreSQL 전체 프로토콜 검증은 별도 통합 테스트 결과입니다.

두 저장소를 함께 동일한 과거 상태로 되돌린 경우와 악의적인 DB 관리자/호스트 변조는 탐지 보장 범위가 아닙니다.
기존 비보호 기본 저널을 사용하는 다른 코드와 외부 프로그램도 범위 밖입니다.
실제 계정 주문 사용량, 외부 IP 용량, 비용 상한 증명은 여전히 미확인입니다.

보조 스키마 생성과 새 저장소 바인딩은 명시적 API이며 클라우드 격리 테스트에서만 수행했습니다.
운영 시작 시 자동 스키마 생성·기존 파일 채택·재설정·복구는 하지 않습니다.
운영 CLI·Windows 설치·Windows DB 변경·거래소 요청·실제 주문·거래 재개: 0.
