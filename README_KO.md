# 청산 준비 대조를 줄이는 후보 — 검토 전용

소스 `b804197c5ff16c2e2a860f7c2a71b9c1913d8bf8`
직전 후보 `2ea564f4c146edc836161a2b873d07b6a8ea129a`
Windows 설치 기준 `4e967dc6751c6f04786ba63cdcc97e7eb1c80a39`

이 패키지는 설치용이 아닙니다. CLI에서 새 구성요소를 참조하지 않으며, 실제 DEMO/LIVE 거래와 Windows DB에 접근하지 않았습니다. 기존의 기본 실행 거부와 6,000 한도 진입 차단은 유지합니다.

## 변경 내용

원래 PAUSE_ENTRIES 명령은 그대로 전체 대조를 수행합니다. 그 직후, 이 후보가 예약한 하나의 전량 체결·보호된 BTCUSDT DEMO 검증 주문만 관리 중이고 계정이 NORMAL·일시정지·대조 완료인 경우에 한해 계정 상태 전체의 해시와 작업 소유자/fence를 기록합니다. HTTP 응답을 캐시하지 않습니다.

이어지는 동일 검증 작업의 EMERGENCY_FLATTEN 명령에서:

1. 같은 fenced DB 트랜잭션 안에서 계정 상태 전체가 같고 경과 시간과 대조 시각이 모두 2초 이내인지 확인합니다.
2. 새 전체 이력 스냅샷을 1회 조회합니다. 전 종목 포지션, 일반/Algo 주문, 모드, 계정/재무 값, 과거 주문 조회 및 income 페이지를 그대로 읽습니다. fingerprint뿐 아니라 입출금 이력도 별도로 비교합니다.
3. 모두 같을 때만 긴급청산 의도를 기록하고 원래 _flatten 함수를 호출합니다. 이 함수의 실제 포지션 재조회, 원래 ID/불명확 응답 처리, fenced DB 효과와 reduce-only 정책은 바꾸지 않았습니다.
4. 명령 결과는 항상 UNKNOWN입니다. 기존의 전체 confirm_flat 절차만 최종 성공을 판정합니다.

상태 변경·시간 초과·비정상 시계·대상 범위 불일치에는 기존 긴급청산 대조 경로를 사용합니다. 새 스냅샷 조회가 실패한 경우에도, 청산 요청을 아직 시도하지 않았을 때만 기존 메타데이터 장애/최소 포지션 확인 정책으로 복귀합니다. 이는 원래 대조 단계가 다시 조회하는 동작이며 추가 비용이 발생할 수 있습니다. SDK 418/429에서는 복귀 조회 없이 원래 쿨다운을 유지합니다. 청산 전송 가능성이 생긴 뒤에는 복귀나 POST 재전송을 하지 않습니다.

동일 명령을 다시 받으면 UNKNOWN을 반환하고 주문을 재전송하지 않습니다. 같은 인스턴스의 동시 명령은 직렬화하고, DB에 이미 기록된 동일 명령도 새 효과를 수행하지 않습니다. 다른 명령이나 작업에는 후보 경로를 적용하지 않습니다. 전체 계정의 외부 쓰기나 공유 IP 용량을 잠그는 기능은 아닙니다.

## 검증

**107개 통과**: 비용 비교 10개, 상태 변경·오류·응답 유실 등의 전체 파이프라인 14개, 대상 범위·잠금 입력·동시 중복 명령 15개, 새 구성요소로 재검증한 진입 예산 통합 14개, 직전 단계의 취소 대기 안전 검사 24개, 기존 예산 단위 검사 30개입니다. Ruff와 mypy(136개 운영 소스 파일)도 통과했습니다.

실제 PostgreSQL의 분리 스키마와 로컬 WSS를 사용하며 HTTP/주문/체결은 모두 가짜입니다. 시간 초과, 역행/NaN 시계, 계정 및 입출금 변경, HTTP500, 429 쿨다운, 불완전 income 이력, 청산 응답 유실, 청산 직전 TP 체결, 잘못된 fence, 동일 명령 반복/동시 호출을 검증했습니다. 대상 범위 검사에서는 기존 경로 호출을 대체해 후보가 손실 잠금 등의 상태를 변경하지 않고 복귀하는지 분리 검사했습니다. 전체 파이프라인에서는 원래 위험·청산 정책을 유지합니다.

관찰 시간은 테스트에서만 0.8초 또는 2초입니다. 운영 300초 상수는 바꾸지 않았으며 이번 후보의 실제 300초 시험은 하지 않았습니다. 가상 한도 100,000, 변경 요청별 비용 40을 가정했습니다. 엔드포인트 비용 상한, 공유 IP 확보, 별도 주문 횟수 제한은 증명하지 않았습니다. 불일치 시 복귀 경로는 이번 성공 경로보다 더 비쌀 수 있으므로 기존 청산 예산 가정을 낮추면 안 됩니다.

## 파일과 다음 개발

source/와 source.patch는 현재 설치 기준 대비 누적 변경 파일 18개입니다. handoff-only.patch는 직전 후보 대비 추가 파일 6개만 담았습니다. 원래 설치 CLI/파서/청산/최종 확인 파일은 직전 후보와 동일하며, 누적 설치 기준 차이에는 기존 demo_validation.py의 선택적 훅 6줄이 포함됩니다. 전체 시험에는 기준 저장소와 의존성이 필요합니다.

cost_reports/는 최종 비교 10개, handoff_safety_reports/는 오류 주입 14개, admission_reports/는 새 구성요소 재검증 기록 13개입니다. 요청 쿼리·키·서명은 기록하지 않습니다. manifest는 자기 자신을 제외한 파일 SHA256 목록입니다.

다음 검토 대상은 취소 ACK가 아직 반영되지 않은 첫 최종 확인 시도에서 반복하는 전체 대조입니다. 기존 전체 성공 증명, 새 계정 변경 감지, 보호 손절과 펜싱을 보존할 수 있는지 먼저 입증해야 합니다. 현재 Windows는 계속 일시정지를 유지하며, 이 코드를 컨테이너에 복사하거나 거래를 재개하지 마세요.
